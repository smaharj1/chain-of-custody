# Settings templates (report section 7.2)

Per-project settings belong to the project (A28). The kit ships templates and never overwrites a project's `settings.json` on upgrade (CO-33). Everything in this directory except this file is **generated** from `${CLAUDE_PLUGIN_ROOT}/scripts/guards/hooks.manifest.json` and the sandbox profile by `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/guards/wiring.py --write`; `--check` (run by the tests) fails when they drift. Do not edit them by hand.

| File | What it is | Used by |
|---|---|---|
| `interactive.settings.json` | An allow template with **named scripts only** (`Bash(npm run test:*)`, not `Bash(npm:*)`), an `ask` list for the git writes, the deny block, `enableAllProjectMcpServers: false`, and the sandbox profile | A human merging it into their `.claude/settings.json`. Replace the example scripts with the project's own |
| `headless-child.settings.json` | The profile a driver child is started with, as `--settings <file>`: `permissions.defaultMode: dontAsk`, an explicit allow list, the deny block (which includes `Workflow`, RC-17), no project MCP servers, the sandbox on, and `env: {}` for the driver to fill. It carries no `hooks` block: the driver starts the child with `--plugin-dir`, so the guards come from the plugin's `hooks/hooks.json`, and loopctl refuses child settings that wire hooks | `loopctl run` (the driver) |
| `critic.settings.json` | The same, for a critic child: Edit, Write, MultiEdit and NotebookEdit denied, no installs | the driver, for `code-reviewer`, `design-critic`, `security-reviewer` |
| `deny-baseline.json` | The deny block alone | `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/doctor.py` diffs the effective settings against it (`guards.deny-drift`) |

## The deny block

Infrastructure mutators (`terraform apply|destroy|import|state`, `cdk deploy|destroy|bootstrap`, `pulumi up|destroy`, `kubectl apply|delete`, `helm install|upgrade|uninstall`, `sam deploy`, `serverless deploy`, `fly|vercel|netlify|wrangler|railway` deploys, `aws cloudformation deploy`, `aws s3 rm|sync`, `aws iam`), `sudo`, privileged Docker and `docker push`, `Bash(claude:*)` and `npx @anthropic-ai/claude-code`, pushes to `main`/`master` and force, delete, mirror and tag pushes, `commit --no-verify`, `gh pr merge|release|secret|workflow run|repo edit`, `Read` of `.env` files except `.env.example` (and `~/.aws`, `~/.ssh`, `~/.config/gh`), `Edit` of the guardrail paths, `mcp__*__run_script`, `mcp__*deploy*`, and `Workflow`.

It is a typo guard (P25): permission deny rules are not a security boundary, and Read/Edit rules do not cover what a subprocess does. It is still worth having because it works in bypass mode, and it is the second layer under the guards, which deny the same commands (the tests check that every `Bash(...)` entry is also refused by the guards).

## Sandbox

`sandbox.enabled: true`, `failIfUnavailable: true`, `allowUnsandboxedCommands: false`, no `docker` in `excludedCommands`, the network allowlist with `169.254.0.0/16` denied, `denyRead` on credential directories and `denyWrite` on the whole H6 write set: `.git/hooks`, `.git/config`, `.git/info`, the session registry `.git/loopctl/sessions`, every settings file, `.claude/hooks|scripts|agents|skills|commands|rules|workflows`, `.claude/loop.config.md`, `.claude-plugin`, CI definitions, `.mcp.json`, CODEOWNERS (the list is `SANDBOX_DENY_WRITE` in `guards/paths.py`; ${CLAUDE_PLUGIN_ROOT}/docs/security/sandbox.md says what it does not cover). In a linked worktree add the absolute git-dir paths: `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/guards/wiring.py --sandbox-snippet`. The source is `${CLAUDE_PLUGIN_ROOT}/templates/security/sandbox.settings.json`; the key names follow the report and are unverified against a live CLI (V19). Mandatory from L2.

## Not in these files

- **Model pinning and fork mode.** `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` (when a model profile is pinned) and the fork-mode and background-task variables go into the child's `env` block, per runner, written by the driver (report 11.3, 11.4). The template leaves `env` empty.
- **Managed settings** for L3 and above (`allowManagedHooksOnly`, `permissions.disableBypassPermissionsMode`, the full guard wiring as managed hooks, since `allowManagedHooksOnly` turns the plugin's hooks off): `${CLAUDE_PLUGIN_ROOT}/templates/security/managed-settings.example.json`, generated by `wiring.py` with the others.
- **MCP lockdown.** The deny block already refuses the deploy-class patterns (`mcp__*__run_script`, `mcp__*deploy*`, `mcp__*apply*`, `mcp__*destroy*`, `mcp__*terminate*`, `mcp__*provision*`, `mcp__*rollout*`, `mcp__*change_set*`, create/update/delete stack); the fuller snippet (`enabledMcpjsonServers`, per-server denies) is `${CLAUDE_PLUGIN_ROOT}/templates/security/mcp-lockdown.settings.json`, which carries the same list as `${CLAUDE_PLUGIN_ROOT}/templates/infra/mcp-deploy-deny.settings.json`.
- **Modes never edit settings.** They print a snippet for the human (CO-16).

## Where the guards are wired

Only in the plugin: `${CLAUDE_PLUGIN_ROOT}/hooks/hooks.json`, generated by the same `wiring.py --write`. No template here carries a `hooks` block, and a project's `.claude/settings.json` must not wire the kit's guard scripts again (they would run twice), must not set `disableAllHooks`, and must not set the plugin to `false` in `enabledPlugins`. `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/guards/wiring.py --check --project <dir>` and the doctor's `guards.wiring` check say when one of these holds; `guards.v1-residue` reports the removed v1 hooks `guard-git.sh` and `guard-main-edit.sh`.
