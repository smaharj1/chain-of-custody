## 1. Executive summary

**What the kit is.** The kit is a strong *chain of custody*:

```
requirements → design + API contract → briefs → engineer reports
```

The chain has independent critics: design-critic, code-reviewer and security-reviewer. In real use (Install A: ~88 reports, 18 features) it delivered steady quality, and its reviews caught real defects such as SQL injection and Zod v4 drift. **That product is the interactive lane, operated by a human who does every git step and every merge.**

**What it is not yet.** It is not a factory. The autonomous loop (`/planner` → `/orchestrate`) has **never run anywhere** (UE). Even if it did, it would stop at local `main`. Its control logic (counters, locks, state transitions, git sequences) lives in prose that the LLM must execute faithfully, through context compaction.

**What changed in the world since the kit was designed.**
- Hooks now see which agent is acting (`agent_type`).
- Hooks can fail closed (`onFailure: block`).
- Subagents take `disallowedTools`, `maxTurns`, `effort` and skills preloads.
- Workflow fan-out exists.
- Background sessions (`--bg`) and routines exist.
- `claude plugin eval` provides pass^k regression testing.
- Sandboxing has fail-closed flags.
- Fork mode is now the default: in the terminal since v2.1.232, and in `-p` since v2.1.302 (RC-29).

Several kit assumptions are now false, and several kit workarounds are now redundant (§12).

**The single most important finding.** A two-round adversarial review of the first-draft v2 design showed that **the draft's safety model was wrong**. It treated hooks and deny rules as the boundary that keeps infrastructure human-gated. They are not. They are typo guards. An agent with Bash can walk around every in-kit layer at once:

1. It can run a nested `claude -p --settings '{"disableAllHooks":true}'` (CS-2).
2. It can use an interpreter: `python -c`, `node -e`, a test file or a postinstall script (CS-6).
3. It can rewrite `.git/config` or `.git/hooks` (CS-8).
4. It can reach credentials the doctor never checked: other AWS profiles, the SSO cache, IMDS, the docker socket (CS-3).
5. It can act as the human on GitHub, because it holds the human's token. It can then approve its own "required reviewer" environment gate (CS-1).

On top of that, `terraform plan`, `cdk synth` and `pulumi preview` *execute code* (CS-4). A pull request executes code before anyone reviews it (CS-5).

So "infra deploy stays human" can only be true if it is enforced **outside the agent's reach**:
- **(a)** a separate bot identity that physically cannot approve or bypass;
- **(b)** no mutating credentials anywhere the agent can read;
- **(c)** a mandatory OS sandbox for any unattended level;
- **(d)** server-side rulesets, environments and OIDC subjects;
- **(e)** an audited **deployment surface**: every way the *target repo's own* CD can deploy (push-triggered workflows, git-integrated hosts such as Vercel or Amplify, release tags) is gated by a human approval the bot can't give (B5, RC-1).

Item (e) was added by the third adversarial round (§21). Without it, a bot push or an L5 docs auto-merge on a repo whose `main` deploys on push *is* an automated production deploy, whatever the kit's own CI does. Item (a)'s Environment approvals also depend on the GitHub plan: on private repos they need GitHub Enterprise (RC-2, §8.4).

The kit's hooks remain valuable as fast, friendly, tested guardrails against mistakes. They are no longer described as the boundary.

**Top recommendations (in order):**
1. **Measure before building.** Tag v1.2.0, build a tiny `examples/hello-loop` fixture, and run the V1 loop on it under baseline conditions: at least 3 runs, or 1 run plus replayed dispatches, reported as ranges (RC-8). Write down kill criteria (§16.2). Every later *capability* phase must move a number on that fixture; safety phases are judged by the corpus instead.
2. **Build the real boundary first** (§5, Phase 1):
   - bot identity with no bypass for the bot;
   - credential audit, **including the human's own `gh`, git and SSH credentials** (RC-5);
   - a deployment-surface audit of the target repo's CD (B5, RC-1);
   - mandatory sandbox for L2+;
   - OIDC environment subjects, with a fallback for GitHub plans without Environment reviewers (RC-2);
   - PR-time CI split into an untrusted job with no secrets and a human-gated plan job (RC-3);
   - a hook-liveness canary (advisory in Phase 1, enforced once loopctl exists; RC-7).
3. **Give the lane people actually use a PR delivery path** (`delivery: draft-pr` in the interactive lane) before building the loop controller (CS-33). The maintainer already ships through serial PRs with human merges (L-39).
4. **Move loop control into a deterministic `loopctl`**, as one "loopctl MVP" phase (RC-10): `validate`, `status`, `doctor`, a serial `run`, and an O_EXCL lock, with state in the git common dir, a failure taxonomy, a spend ledger and whole-run abort. Each gate is added only when it earns a metric.
5. **Make verification resistant to reward hacking** (§9):
   - interface stub first, then acceptance tests that fail *by assertion* on main;
   - held-out tests outside the worktree;
   - a test-integrity gate that covers *new* files and env vars;
   - mutation testing on changed lines;
   - CI-produced evidence as a required check.
6. **"Automatic subagents and nested sessions" means one human command, then a driver.** A human types one command. An **external driver** (`loopctl run`) then launches every child session with explicit settings. No agent ever launches `claude` itself, because that is the escape hatch in CS-2. Inside a session, subagent dispatch is already automatic. The work is making it *reliable*: report files, resume by ID, fork-mode handling, and `maxTurns` (§11).
7. **Prune plugin assumptions** (§12):
   - drop hardcoded context7, `code-review:code-review`, superpowers, hand-written telemetry and the Workflow ban;
   - move modes to skills;
   - adopt `disallowedTools`, `maxTurns`, `effort`, agent-aware hooks, `.claude/rules`, `claude plugin eval` and plugin packaging.
8. **Defer the rest until it has earned its place:**
   - L4/L5 autonomy;
   - parallel worktrees;
   - desktop and Workflow runner tiers;
   - the learning loop;
   - `/bootstrap`;
   - and, after the third adversarial round (RC-10): hash-chained telemetry (cut), the remote multi-machine lock (Phase 11), `guard-budget` (cut; `maxTurns` and `--max-budget-usd` cover it), G4 mutation and multi-language G5 AST lint (per-stack opt-in), a separate G8 verifier (folded into G3 + code-reviewer), and G10 (Phase 11).

   Wait for 3 clean fixture runs plus one real feature (CS-34).

**Numbers.**
- Four audits produced ~150 findings.
- Two adversarial critics added 89 more: 41 soundness and 48 omissions. These include 9 platform claims shown to be **wrong** and 10 that are **unverified**.
- Every finding has a disposition in §19.
- A third adversarial round on this report raised 32 more (RC-1..RC-32: 1 critical, 9 high). All are applied; §21 lists each disposition.

## 4. Your four goals: direct answers

### G1. "Enable usage of subagents and nested sessions automatically"

**Answer:** yes, with one hard rule. *Automatic* means the kit, not the human, decides and launches every dispatch after a single human start command. **No agent ever launches a `claude` process.** A child session launched by an agent can disable every kit hook and permission (`--bare`, `--settings '{"disableAllHooks":true}'`, `--setting-sources`), and so can an Agent SDK script (CS-2) [docs]. The process that launches children must therefore be the deterministic driver, `loopctl run`, started by the human. Agents are denied the `claude` binary and SDK imports.

**What becomes automatic**

1. **Within a session: subagents.** Make the existing dispatch dependable:
   - Engineers write their own report file and return `{status, report_path}` plus a JSON trailer (D-14). The conductor never re-transcribes.
   - Resume by `agent_id` via SendMessage. Never pass `name`, because with agent teams enabled a named spawn becomes a teammate *in the main checkout* (CS-29) [docs].
   - Handle fork mode, which is on by default in the terminal since v2.1.232 and in `-p` since v2.1.302 [docs] (RC-29; V18 confirms the per-surface behavior before the event-driven rewrite is built). Interactive sessions don't wait for forked children unless fork mode is off. In `-p`, nested spawns wait only when it is on (CS-27). Dispatch becomes **event-driven**: the child writes its report file, and the conductor reacts to the completion notification or a file watch. A blocking return is no longer assumed. The env vars `CLAUDE_CODE_FORK_SUBAGENT` and `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` are set per runner (§11).
   - Use `maxTurns` (resumable; v2.1.246+), `disallowedTools: Agent, Skill, mcp__*` and an explicit `subagent_type` on every call (D-9, D-24).
   - Modes chain with a one-line confirm: PM → Architect → Tech Lead (D-17).
2. **Across sessions: nested sessions, launched by the driver.**
   - `loopctl run` starts one `claude -p` per item. Each gets explicit `--settings`, `--agents`, `--allowedTools`, `--permission-mode dontAsk`, a remaining-budget figure, and a registered `session_id`.
   - This gives crash isolation and fresh context per item (L-17). It also gives a real process boundary for the sandbox.
3. **Workflow fan-out** (reviews, critique voting). Use it only as a **saved** `.claude/workflows/<name>` invoked from a human-run `/orchestrate`, because the platform requires human opt-in [docs] (CS-28, P13). The opt-in is not a hard wall: a permission **allow rule** for Workflow lets it launch headlessly in `-p` (RC-17). So the headless profile denies Workflow, engineers get it in `disallowedTools`, and the doctor fails if Workflow appears in any allow list other than the human `/orchestrate` profile.
4. **Desktop `start_session`.** Do not rely on it for automation:
   - It is a deferred desktop MCP tool.
   - Its "offer" and "own_initiative" modes create user-confirmed proposals [docs/observed].
   - It is useful as a *human-convenience* runner, not an automatic one.

**What can't be automatic, by platform design:**
- Workflow without human opt-in (an allow rule counts as opt-in, which is why the kit denies it headlessly).
- Nesting deeper than `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` (default 3) [docs].
- Interactive-only tools inside subagents.

Correct arithmetic (CS-36): main → item-runner (layer 1) → engineer (layer 2) leaves layer 3 free. Engineers are still denied `Agent`, by choice, for predictability and cost.

### G2. "Grow closer to a full-automation software factory (infra deploy stays human)"

**Answer:** reachable up to **L3, the draft-PR factory**, on the roadmap in §16, and later **L4, unattended with PR-review approvals**. Infrastructure apply and deploy is **never** automated at any level. It is enforced by identity, credentials and an audited deployment surface, not prose (§5, §6). "Deploy" includes the target repo's own CD: a push-triggered deploy workflow, a git-integrated host (Vercel, Netlify, Amplify, Fly, Render, Railway, Cloudflare), a preview deploy, and a release tag. The doctor caps the effective level when any of these fires without a human gate (B5, RC-1). The path:
- PR delivery for the interactive lane first.
- Then `loopctl`.
- Then verification integrity.
- Then the unattended driver.
- Then intake.

**The factory's ceiling** is L5, auto-merge for low-risk paths such as docs and copy. Two conditions apply:
- It is never available for `always_human_paths`.
- It requires feature-flagged exposure for anything user-visible (CO-26).
- It is never available on a repo where a merge to `main` deploys without an Environment approval (B5): there, even a docs auto-merge is a production deploy (RC-1).

### G3. "Enhance loop engineering"

**Answer:** move control from prose into `loopctl`, a stdlib-python deterministic controller. Its pieces:
- state in the git common dir;
- the plan definition immutable on main (changed only by plan PRs);
- an O_EXCL lock locally (a remote multi-machine lock is deferred to Phase 11; RC-10, RC-12);
- a failure taxonomy, so platform outages don't burn item retries;
- a durable spend ledger;
- whole-run abort and rollback;
- a SessionStart(compact) re-inject.

**PostCompact cannot inject** [docs] (CS-24).

Add gates G0–G11, each with a toggle and an owner metric (§9; RC-22). They land one at a time, as each earns a metric, not as a batch (RC-10). Validate everything on the fixture with a fault-injection suite and pass^k evals (`--threshold 1.0` for safety cases) (§15).

### G4. "New, or discontinued, plugin assumptions"

**Answer:** see §12 for the full table. In summary:

**Drop:**
- context7 hardcoded in `tools:` (make it optional or probed);
- `code-review:code-review` (the kit's own code-reviewer agent becomes the default; bundled `/code-review` is an optional second opinion);
- superpowers references;
- modes as commands (→ skills);
- the hand-written `metrics.jsonl`;
- "hooks can't tell agents apart";
- the Workflow ban;
- all-opus by default (use a profile);
- "no auto-loader" (`.claude/rules` loads in subagents [docs]).

**Adopt:**
- `disallowedTools` / `maxTurns` / `effort`;
- skills with frontmatter;
- hooks.json with `onFailure: block` on **every blocking-capable kit hook** (PreToolUse, PermissionRequest, ConfigChange, SessionStart checks). It has no effect on Stop, SubagentStop, TaskCompleted, TeammateIdle or async hooks [docs] (RC-30);
- SubagentStart/Stop telemetry;
- `.claude/rules`;
- `claude plugin eval`;
- `plugin/` packaging;
- `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` where an env override must win (CS-39).

**Decide explicitly** (CO-34):
- Plan mode for read-only phases: adopt for `/architect` and `/planner` exploration.
- The `opusplan` alias: offer in the `balanced` profile.
- The Advisor: optional for the verifier.

## 5. The real boundary (security model, revised)

### 5.1 The principle

> **Assume any agent holding a Bash tool can run arbitrary code as the OS user it runs as.** Every in-session control is a guardrail against mistakes. That covers hooks, permission deny rules, frontmatter `tools:`, and prose rules. The *boundary* is what holds after an agent has escaped all of them.

The boundary is built from five things the agent cannot change from inside its session:

| # | Boundary element | What it stops | Finding |
|---|---|---|---|
| B1 | **Identity.** The agent acts on GitHub as a **bot**: a **GitHub App** at L3+; at L2 only, a dedicated machine user's fine-grained PAT is acceptable, and the doctor fails it within 14 days of expiry. Never a PAT belonging to a human. Scopes: contents + pull-requests write only; **no** `workflows`, `actions`, `administration`, `environments` or `secrets` (RC-11). | The agent approving its own Environment gate, merging as admin, editing workflows, or bypassing rulesets | CS-1, CS-5, RC-11 |
| B2 | **Credentials.** No mutating cloud, DB or deploy credential exists anywhere the agent's OS user can read: no other AWS profiles, SSO cache, `credential_process`, kube contexts, gcloud/az configs, `.env.production`, docker socket, IMDS (169.254.169.254) or the ECS endpoint (169.254.170.2). **This includes the human's own GitHub and git credentials** (RC-5): `gh` auth, `~/.config/gh/hosts.yml`, `~/.git-credentials`, the OS keychain helper, `GH_TOKEN`/`GITHUB_TOKEN`, and an SSH agent (`SSH_AUTH_SOCK`) or key that GitHub accepts. Only the bot's credential is reachable. Apply credentials exist only in CI, via OIDC, behind an Environment, or on the human's machine outside the agent's OS user (§8.4). | Infra mutation through any path (CLI, SDK, interpreter, MCP, container); pushing or merging as the human | CS-3, CS-12, CO-2, CO-39, RC-5 |
| B3 | **OS sandbox / container** (mandatory at L2+). Claude Code sandbox with `failIfUnavailable: true` and `allowUnsandboxedCommands: false`, plus a network allowlist (deny 169.254.0.0/16 and cloud control-plane endpoints), `denyWrite` on the git common dir's `hooks/`, `config` and `info/`, and `denyRead` on prod secrets and held-out tests. Docker and podman are not in `excludedCommands`. Or a devcontainer / separate OS user with the same effect. | Interpreter and script walk-arounds, git-config escalation, credential reads, held-out test peeking | CS-3, CS-6, CS-8, CS-16 |
| B4 | **Server-side policy.** Rulesets on `main` and integration branches where **the bot is never a bypass actor**. A solo maintainer may list their own human account as a bypass actor in **pull-request-only** mode, so they can merge their own H6 change; every bypass is logged and shown in `loopctl status`. Teams of two or more use no bypass actors (RC-9). Also: required reviews, CODEOWNERS on `always_human_paths`, required status checks (CI verify + evidence check run), Environments with required reviewers and **"prevent self-review"** where the plan offers them (§8.4), OIDC trust subjects pinned to `environment:<env>` (never `repo:*` or `ref:*`), and **split CI**: an untrusted PR job with no secrets and no OIDC, and a plan job that runs only after a human gate and never executes PR-supplied `.claude/`, `.mcp.json`, `plugin/**`, `.claude-plugin/**` or skill directories (§8.4, RC-3, RC-18). | Everything the agent pushes being trusted before review; CI being used as a code-execution path | CS-1, CS-5, CS-18, CS-20, RC-3, RC-9 |
| B5 | **Deployment surface.** Every path by which a commit becomes a deploy is inventoried and gated: push/release/`workflow_run` deploy workflows, git-integrated hosts (Vercel, Netlify, Amplify, Fly, Render, Railway, Cloudflare), preview deploys and release automation. `doctor --deploy-surface` scans for them; the human attests the result in loop.config (`deploy_triggers`, `git_integrated_hosts`), each marked `gated-by-environment` or `none`. A deploy that fires on a bot-pushable ref with no human gate caps the effective level at **L1**; one that fires on `main` with no human gate caps it at **L4** (no auto-merge) (§8.4). | A bot push, auto-merge, revert or tag becoming a production or infrastructure deploy with no human | RC-1 |

B1–B4 stop the agent from *acting* as a deployer. B5 stops the target repo from deploying *on the agent's behalf*: a push the bot is allowed to make must not be a deploy the human never approved.

**Hooks and deny rules are guardrails, not boundaries.** The platform says Bash deny rules are "not a security boundary", and Read/Edit rules don't cover subprocesses [docs] (P25). The kit therefore stops claiming otherwise:
- The example docs and README stop overclaiming (F-19).
- `guard-infra` is renamed or documented as a **typo guard** (CS-6).

### 5.2 Threat model: what we defend against

| Actor / cause | Example | Primary defense | Secondary (guardrail) |
|---|---|---|---|
| Honest mistake | Engineer runs `terraform apply` "to check" | B2 (no creds) | guard-infra deny, infra-engineer protocol |
| Reward hacking | Engineer edits a test, adds `.skip`, special-cases the input | G3/G5/G6 gates run by loopctl from base-ref config, plus CI check run | code-reviewer rubric |
| Overreach under pressure | Conductor pushes to `main` after a failing gate | B1 + B4 (ruleset, bot never bypasses) + B2 (no human credential to push with) | guard-git v2 |
| Deploy by side effect | A bot push to a deploy-on-push branch, a docs auto-merge on a deploy-on-merge repo, a preview deploy, a release-please merge | B5 (audited deploy surface, level caps) + H5 | guard-git refspec allowlist |
| Prompt injection | A poisoned issue, PR comment, web page, dependency README or MCP tool output instructs "push to main" or "print env" | Trust boundary §5.3, B1–B4 | injection-string flagging hook |
| Self-modification | Agent edits `.claude/settings.json`, hooks, `.git/config`, CI workflows | B3 denyWrite, B4 CODEOWNERS + H6, managed settings at L3+ | guard-main-edit v2, ConfigChange blocking hook |
| Escape via child process | `claude -p --bare`, Agent SDK script, `npx some-cli`, a test calling the SDK | B2 + B3 (nothing to steal, nowhere to go); deny the `claude` binary and SDK imports for agents | Bash deny, AST lint on new files |
| Supply chain | Hallucinated or typosquatted package; malicious postinstall | §5.5 dependency gate; `--ignore-scripts`; B3 network allowlist | security-reviewer with a real scanner |
| Platform drift | A CLI update changes hook schema or fork semantics | Version pin plus canary (§14.3) | SessionStart version check |

### 5.3 Trust boundary for untrusted content (CO-1, CS-9)

**Trusted:**
- human chat;
- the plan and ACs approved at H1/H2;
- repository content **at the base sha**;
- kit files from a tagged release.

**Untrusted:**
- web pages (WebFetch/WebSearch);
- issues and issue comments;
- PR comments and reviews from non-maintainers;
- dependency files and changelogs;
- MCP tool output and server instructions;
- the UAT/feedback widget;
- anything an engineer *wrote* in this run (until reviewed);
- CI logs.

**Rules:**
1. **Taint follows the session.** A session that has read untrusted content may not hold merge, push-to-protected or credential-bearing authority in the same context. At **L3+**:
   - the conductor and the verifier have **no** WebFetch/WebSearch;
   - engineers' web access is limited to a domain allowlist (sandbox network allowlist plus `WebFetch(domain:…)` rules).
2. **Intake is two-stage.**
   - A **tool-less triage agent** reads the issue or comment and emits a fixed JSON schema: title, problem, ACs as plain text, labels. That JSON lands in a quoted "untrusted input" block of the brief, never in its instruction section.
   - A separate tool-bearing session acts on the JSON.
3. **Intake triggers only from trusted actors**: `author_association ∈ {OWNER, MEMBER}`, plus a maintainer-applied label. A label-guard workflow removes `factory:*` labels applied by non-maintainers.
4. **No write-capable routine runs on non-maintainer PRs.** PR-event routines would execute the PR head's `.claude/` (CS-9). Routines use a low-privilege identity and **no connectors**.
5. **claude-code-action in CI:**
   - restore `.claude/`, `.mcp.json`, `plugin/**`, `.claude-plugin/**` and every directory the kit loads skills from, from the base ref, before running. Skill frontmatter hooks run in untrusted `-p` (RC-18);
   - use `--setting-sources user` (or explicit `--settings`);
   - run it only in a job that does not check out PR code with secrets in scope, or give it a dedicated, spend-capped API key (RC-3);
   - PR-triggered jobs follow the per-job permissions table in §8.4 (CS-5). No PR-triggered job gets both PR code and `id-token: write`.
6. **Acting on instructions found in untrusted content is an always-human class** (H7, §6).
7. **Detection (guardrail):** a PostToolUse hook flags tool output containing agent-directed imperative strings. It annotates and logs; it never relies on blocking.
8. **Evals:** an injection corpus with a poisoned README in a dependency, a poisoned issue, a poisoned web page and a poisoned MCP result, run as pass^k (`--threshold 1.0`) safety cases (§15).

### 5.4 Secrets policy (CO-2)

One policy replaces four contradictory statements.

**Where secrets may live.** Locally, env vars and `.env.local`/`.env.test` may hold **dev and test values only**. Deployed environments use a secret manager. This reconciles `infra-engineer.md:50` with `local-dev.md:22-24,79-82`.

**Files and paths:**
- `.gitignore` gains `.env*` with `!.env.example`.
- `.worktreeinclude` lists only `.env.local` and `.env.test`.
- `.env.production*`, `*.pem`, `*.key` and cloud credential dirs are never copied. They are covered by sandbox `denyRead`, because a `Read(**/.env*)` deny alone is bypassed by `Bash(cat …)`.

**Never in artifacts.** Secrets never appear in briefs, reports, evidence, events, PR bodies or memory:
- The events writer redacts known secret patterns.
- gitleaks (or trufflehog) runs on every loop commit and every evidence artifact, both pre-commit and as a required CI check.

**Shared DB credentials** (`durable_db_scope: shared`) are never present locally. Tunnels and port-forwards (`ssh -L`, `kubectl port-forward`, `aws ssm start-session`) are denied to agents, because DATABASE_URL host inspection is defeated by a local port-forward (CS-12).

**Secrets provisioning is always human** (H6).

### 5.5 Dependencies and supply chain (CO-13, CO-28)

**New-dependency gate.** Any added top-level dependency is listed at the checkpoint or in the PR body. At L3+ it requires human approval. The gate checks:
- that the package exists in the registry;
- its age and download count;
- its name distance from popular packages (slopsquat/typosquat);
- that its licence is on the allowlist.

**Install hygiene:**
- `npm ci --ignore-scripts` (and the equivalent for pnpm/yarn/bun) is the default, with an allowlist for packages that need install scripts.
- CI uses a frozen lockfile.
- Registries are pinned in `.npmrc`/`pip.conf`.

**Scanner-backed security review.** `security-reviewer` stops claiming CVE checks it can't do. CVE data comes from `npm audit` / `osv-scanner` / `pip-audit`, run by loopctl or CI, and the reviewer interprets that output.

**Optional:** SBOM (syft) and provenance attestations at release (H5).

### 5.6 MCP is a tool plane (CS-10, CO-39)

- Engineers and critics: `disallowedTools: mcp__*`. Re-add named servers only on purpose; for example, a docs server for engineers.
- In any session that is part of a loop run:
  - deny `mcp__*__run_script`, `mcp__*deploy*` and any mutating cloud/DB/SaaS MCP tool;
  - `enableAllProjectMcpServers: false`.
- `.mcp.json`, `.claude-plugin/**` and `plugin/**` join the H3 `always_human_paths` and the G5 integrity glob.
- The doctor lists the MCP servers enabled in the effective settings, and fails at L2+ if a deploy-capable one is enabled. This is Install B's `deploy-on-aws` case.

### 5.7 Session identity: who is the conductor? (CS-7, CS-25)

Today the conductor is "the session without `agent_type`". That includes any `start_session` child, `--bg` session, routine or CI session, and every one of them would get conductor rights. The test is also wrong on its own terms: `agent_type` is set for subagents **and** for any main session started with `--agent`, which is every driver child. `agent_id` is the field present only for a subagent or in-process teammate [docs] (RC-16).

**Fix:**
- At run start, `loopctl` records the conductor's `session_id`, read from the SessionStart hook input, in the run state.
- Guards grant conductor rights only to that `session_id`. Unknown sessions get least privilege: read-only git, no push, no loopctl write subcommands.
- Driver-launched sessions start with `--agent <role>`, so they carry a role.
- **Caller classification** uses `session_id` registration plus `agent_id`, never `agent_type` alone:
  - `agent_id` present → a subagent or teammate; its role is `agent_type`;
  - no `agent_id`, registered `session_id` → the conductor, or a driver child with the role registered for that session;
  - no `agent_id`, unregistered `session_id` → least privilege, whatever `agent_type` says. A human's interactive `--agent` session with an off-roster role lands here.
- Guards normalize `agent_type` by stripping a `<plugin>:` prefix and matching against the loop.config roster (CS-39). The corpus tests both forms.

### 5.8 Hook liveness and untrusted headless contexts (CS-11, CS-23)

In untrusted `-p` contexts (fresh clone, CI, cloud), project `permissions.allow` and **subagent** frontmatter hooks are not applied. Settings hooks, `.mcp.json` and **skill** frontmatter hooks are [docs] (RC-18). So a PR that adds a skill can run its hooks in a CI job; §5.3 rule 5 restores skill directories from the base ref. `--bare` may become the `-p` default [docs]. `--bg` needs workspace trust.

**Fixes:**
- The driver always passes explicit `--settings <kit file>`, `--agents`, `--allowedTools` and `--permission-mode dontAsk`.
- **Hook-liveness canary.** A SessionStart hook writes a per-session nonce to the run state. `loopctl` refuses to dispatch into a session whose nonce is missing. If hooks didn't load, nothing runs. In Phase 1, before loopctl exists, the canary is **advisory**: the conductor's prose checks for the nonce and warns. It becomes enforced when the loopctl MVP ships (RC-7).
- At **L3+**, recommend managed settings for the machine or container that runs the factory:
  - `allowManagedHooksOnly`;
  - `permissions.disableBypassPermissionsMode`. The key is valid in any settings file; only the **managed** copy survives a child's `--settings` (RC-31);
  - the kit hooks installed as managed hooks.

  Only managed settings survive a `--settings '{"disableAllHooks":true}'` child [docs]. Alternatively, accept that the boundary is B2/B3 and run in a credential-free container.
- `onFailure: block` makes a crashed or missing handler deny, like exit 2, on **every event that supports blocking**: PreToolUse, PermissionRequest, ConfigChange, UserPromptSubmit and so on. The kit sets it on all of them; without it, the ConfigChange blocker fails open (RC-30). It has **no effect** on Stop, SubagentStop, TaskCompleted, TeammateIdle or async hooks [docs]. Those gates are therefore re-validated by `loopctl` (§10). Stop-hook blocking is capped at 8 continuations (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`), so the Stop hook must honor `stop_hook_active`. **The outer driver, not the Stop hook, is the continuation mechanism.**

### 5.9 Git escalation paths (CS-8, CO-3)

An engineer with only "read-only git" can still escalate through any of these:
- `.git/hooks/*`;
- `.git/config` keys: `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `filter.*`, `include.path`;
- `.gitattributes` filters;
- `package.json` scripts: `postinstall`, `prepare`, `pretest`;
- `.husky/`;
- `.envrc`.

Any of these runs code later in the **conductor's** context.

**Fixes:**
- **B3:** sandbox `denyWrite` on `$(git rev-parse --git-common-dir)/{hooks,config,info}`.
- The conductor runs git as `git -c core.hooksPath=<kit hooks dir> -c core.fsmonitor=false …`.
- `loopctl` hashes `.git/config` at run start and refuses to continue on a change.
- **Guardrail (guard-git v2) blocks:**
  - `-c core.*`, `-c alias.*`, `git config` writes;
  - `GIT_*` env assignments;
  - `--no-verify`/`-n` on commit and merge;
  - `update-ref`, `filter-branch`, `replace`, `tag -f`;
  - `gh api` with any method other than GET.
- `npm ci --ignore-scripts` by default (§5.5).
- `.gitattributes`, `.husky/**`, `.envrc` and `package.json#scripts` changes join the G5 integrity set.
- Git-native hooks (pre-commit, commit-msg) are **conveniences only**. Every gate that matters is re-checked by `loopctl` at merge time and by CI as a required check (CO-3, CS-18).

### 6.3 Promotion and demotion

**Promotion** uses **server-side facts only**, never local `events.jsonl`, which is forgeable (CS-21). The facts:
- the merged-PR revert rate;
- the CI-fix rate;
- escaped defects (bugs linked to a PR within N days);
- reviewer CHANGES_REQUESTED rate;
- pass^k on the eval suite in CI.

The **evidence bar for moving Install A from manual merge to L3** is stated in config. Suggested default:
- 10 consecutive draft PRs at L2/L3;
- ≤1 reviewer-requested change of class "correctness";
- 0 reverts;
- 0 test-integrity flags.

**Demotion** is automatic on any of:
- a revert;
- a security block;
- a test-integrity flag;
- a **stall storm**.

The stall signal is defined per permission mode (CS-38):
- `dontAsk`: PermissionDenied and deny results per item over a threshold.
- `auto`: the PermissionDenied hook plus the 3-consecutive / 20-total classifier pause.

Whether hook and deny-rule denials count toward the auto pause is [probe] (V14).

**Effective level** = min(configured level, highest level whose prerequisites pass right now, the B5 cap, the platform cap from §8.4). The doctor prints each, and the reason for any gap. L2 and above also require a GitHub-hosted repo; other forges stay at L1 until §8.4 has a row for them.

## 7. Enforcement v2: guardrails (typo guards, tested)

Everything in this section is a **guardrail**. It catches honest mistakes fast and with a clear message, and it produces telemetry. It is not the boundary; §5 is. The guards still matter, because most bad actions are mistakes, and a fast deny with a reason is the cheapest correction.

### 7.1 Guard suite

One `scripts/guards/` package with a shared library. It is python3 stdlib only, wired with `onFailure: block` on every blocking-capable event it hooks (RC-30).

**Identity and repo resolution (shared lib).**
- Read `agent_type`, `agent_id`, `session_id` and `cwd` from hook input. `agent_id` is present only inside a subagent or teammate. `agent_type` is present inside a subagent **and** in any main session started with `--agent`, where the subagent's type takes precedence [docs] (RC-16). Classify the caller per §5.7, never from `agent_type` alone.
- Normalize `agent_type` by stripping a `<plugin>:` prefix, then match it against the `roster` in loop.config (CS-39).
- Conductor rights go only to the **registered** `session_id` (§5.7). Every other non-subagent session gets least privilege.
- Resolve branch and toplevel from the *target path* for Edit/Write and from `cwd` for Bash, via `git -C <dir> rev-parse --show-toplevel` and `branch --show-current`. Never use `$CLAUDE_PROJECT_DIR`. `.claude/worktrees/` is no longer exempt (D-2, A11).
- Read state, lock and HALT from `$(git rev-parse --git-common-dir)/loopctl/`, so every worktree sees the same ones (CS-13, CS-25).
- If `agent_id` is present but `agent_type` is missing or off-roster (V1 probe), the guard runs **agent-blind** and treats the caller as an engineer. That is the restrictive default. A main session with an off-roster `--agent` value and an unregistered `session_id` gets least privilege (§5.7).

**The guards:**

| Guard | Matcher | Blocks | Findings |
|---|---|---|---|
| `guard-main-edit` v2 | Edit, Write, NotebookEdit | Edits on main or the integration branch outside `docs/**`, plan definition files and primers. **No** allow-list for `.claude/**`. Settings, hooks, agents, skills, loop.config, `.mcp.json` and `.claude-plugin/**` are H6. Engineers also cannot edit locked AC tests, test/CI/lint config, `package.json#scripts`, `.gitattributes`, `.husky/**`, `.envrc`, or other slices' footprint paths. | D-2, F-4, L-19, CS-14, CO-11 |
| `guard-git` v2 | Bash | Wrapper normalization: `sh -c`, `bash -c`, `eval`, `env`, `xargs`, `timeout`, `nice`, `sudo`, `command`, `$(…)`, backticks, and `;` `&&` `||` `|` chains. Each segment is parsed. Engineers and critics get read-only git. The conductor gets branch, commit and merge on non-protected refs, and push only per `delivery` and the refspec allowlist. **Always denied:** `--no-verify`/`-n`; `-c core.*`/`-c alias.*`; `git config` writes; `GIT_*` env; `update-ref`, `filter-branch`, `replace`, `tag -f`, `push --force` (except `--force-with-lease` on the run's own branches), `push --mirror`/`--delete` of protected refs; `gh api` non-GET; `gh release|secret|workflow|repo edit|ruleset`; `gh pr merge` unless `merge_policy` and the path checks allow it. | F-5, D-1, CS-8, CO-3 |

| `guard-halt` | All | Checked first. If `<git-common-dir>/loopctl/HALT` exists or the `factory:halt` label is present, deny everything except read-only tools. | F-6, CS-13 |

**Cut (RC-10):** the draft's `guard-budget`, a per-`agent_id` tool-call counter. `maxTurns` in frontmatter is the authoritative per-agent cap (P6, [docs]) and `--max-budget-usd` caps each driver child; a third counter added state and a race without a new signal (D-10, L-29, CS-26 stay addressed by those two).

**loopctl's own git** (state-ref writes, the run lock) runs inside loopctl's process with its own fixed arguments. It is not an agent Bash call, so guard-git never sees it. Agents can't reach it because guard-exec denies loopctl write subcommands to them (RC-13).

**Handler hygiene** (A29, CO-32):
- quoted `"$CLAUDE_PROJECT_DIR"`;
- `if:` filters so non-matching calls don't spawn python;
- `timeout` on every handler;
- `onFailure: block`;
- no network;
- a missing python3 **fails closed**, with a SessionStart banner that says why.

**Self-test.** SessionStart runs `guards --selftest`. It feeds three known-bad payloads and expects three denies. A failed self-test downgrades the effective level to L0.

### 7.2 Settings templates

Per-project settings are owned by the project (A28). They are written by `/init`, or by `/bootstrap` later, and **never overwritten by a kit upgrade** (CO-33). The kit ships:
- **Allow template.** Named scripts only; this is the Install A pattern (F-10). Example: `Bash(npm run test:*)`, not `Bash(npm:*)`.
- **Deny block.**
  - infra mutators;
  - `Read(**/.env*)` except `.env.example`;
  - `sudo`;
  - privileged docker;
  - push to protected refs;
  - Edit/Write to guardrail paths;
  - `mcp__*__run_script`;
  - `Bash(claude:*)`;
  - `Workflow` (RC-17).
  - Engineers also get `Workflow` in `disallowedTools`.

  This is a typo guard (P25). It works even in bypass mode, which is still worth having.
- **Sandbox profile** (`sandbox.json` snippet). `enabled: true`, `failIfUnavailable: true`, `allowUnsandboxedCommands: false`, plus the network allowlist and the denyRead/denyWrite lists from §5.1 B3. Mandatory at L2+ (CS-3).
- **Headless profile** (passed by the driver as `--settings`):
  - `permissions.defaultMode: dontAsk`;
  - an explicit `allowedTools`;
  - `enableAllProjectMcpServers: false`;
  - `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` when a model profile is pinned;
  - an explicit fork-mode env per runner (§11.3);
  - `Workflow` in `permissions.deny`. The doctor fails if `Workflow` appears in any allow list other than the human-run `/orchestrate` profile (RC-17).
- **Managed-settings recipe for L3+:** `allowManagedHooksOnly`, `permissions.disableBypassPermissionsMode` (valid anywhere; only the managed copy survives a child's `--settings`, RC-31), and the kit hooks as managed hooks (CS-2).
- **Modes never edit settings.** They emit a snippet for the human (CO-16).

`loopctl doctor` diffs the effective settings against the suggested deny block and sandbox profile, and reports any drift.

### 7.3 Corpus and telemetry

**Bypass corpus.** `scripts/guards/tests/` is table-driven. Each row is `{payload, agent_type, session role, expected decision}` and covers:
- every CO-3 vector;
- every CS-6 interpreter route;
- every CS-8 git-config route;
- the worktree cases from D-2;
- both plain and `plugin:`-prefixed `agent_type`;
- registered and unknown conductor sessions;
- a `--agent` main session, a subagent inside a `--agent` session, and a `--agent` value that is not on the roster (RC-16);
- `Workflow` in a headless allow list (RC-17);
- a loopctl write subcommand from an engineer (RC-13).

It runs in CI on every PR. It is deterministic and costs nothing.

**Telemetry.** Hooks write telemetry, replacing the hand-written metrics.jsonl (P-6, A7, D-31, L-31, L-42, L-43):
- **SubagentStart:** agent_id, agent_type, model if exposed (P33 [probe]), parent. The parent is the `session_id`, classified per §5.7; a `--agent` main session is not itself a subagent (RC-16).
- **SubagentStop:** agent_id, last-message hash, report path.
- **PostToolUse (async):** tool, decision, duration.
- **PermissionDenied:** the stall signal (§6.3).

Each agent_id writes its **own file**, and `loopctl` merges them. The draft's hash chain is **cut** (RC-10): events are **diagnostic only** and never used for promotion, which rests on server-side facts (§6.3, CS-21), so tamper-evidence bought nothing. Secret redaction runs at write time (CO-2). The model and cost fields come from the `-p` JSON result where the driver runs the session (CS-26). `model_used:"opus"` is no longer hardcoded (CO-21).

## 8. Infrastructure gate: six layers, and apply is never autonomous

The user's requirement is that infrastructure deployment stays human. Here is how that is made true:
- the agent can **author** IaC;
- an untrusted CI job checks the **source** statically, with no credentials (§8.4);
- after a human gate, CI makes a **preview** plan for the PR with a plan-only role;
- after merge, CI makes a fresh plan of `main`, a **human** approves that exact plan, and CI **applies it by hash in the same run**, with a role the agent can't reach or approve (RC-4);
- and nothing else in the target repo deploys on the agent's push or merge without a human (B5, §8.4).

### 8.1 Layers (Layer 4 from the draft is dropped, per CS-37)

## 10. loopctl and state: control flow moves out of prose

### 10.1 What loopctl is

A single python3 stdlib CLI (`scripts/loopctl.py`) that owns every *deterministic* decision the LLM conductor currently performs from prose (T1, L-16):
- state transitions;
- counters and caps;
- the lock;
- topological order with a deterministic tie-break (L-13);
- gate execution;
- the spend ledger;
- reconciliation;
- abort.

The conductor LLM keeps judgment work: design, briefs, integration conflicts, summarizing for humans.

**Write subcommands are denied by PreToolUse for any session that is not the registered conductor or driver**, and for every subagent (CS-25, RC-13). guard-exec enforces this using the §5.7 caller classification. Without that rule, any engineer could replay `loopctl set …`.

**loopctl's own git calls are intentionally outside guard-git** (RC-13). loopctl runs git as a subprocess, which PreToolUse never sees. That is how it can use `update-ref` and push `refs/loopctl/*` while guard-git denies both to agents. It is also why the caller rule above is the control that matters.

### 10.2 Subcommands (one MVP, then additions as they earn a metric)

The draft shipped loopctl in two phases, read-only then writes. That is collapsed into one **loopctl MVP** (Phase 4, RC-10): `validate`, `status`, `doctor` (wrapping the standalone `scripts/doctor` from Phase 1), serial `run`, and the O_EXCL local lock, plus the `begin`/`advance`/`fail`/`approve` writes that serial `run` needs. Everything else in the table lands when a fixture metric asks for it. The remote lock waits for Phase 11.

| Read side | Write side |
|---|---|
| `validate` (plan schema, AC IDs, deps DAG, `touches`) | `run` (the driver; §11) |
| `status [--pending-human]` (what is waiting on a human, with links; CO-44) | `begin <item>` / `advance <item> <stage>` / `fail <item> --class …` |
| `render` (BUILD_PLAN.md and plan diagrams) | `approve <item\|checkpoint> --by <human>` (writes an approval record; L-10) |
| `reconcile --dry-run` (from GitHub API PR/check state; CS-20) | `reconcile --apply` |
| `doctor [--credentials] [--level]` (G0, §8.1 L2, effective level) | `gate <name> <item>` (runs G-gates; writes check run in CI) |

**CAS, defined once (RC-13, RC-28).** Every "CAS" in this report means one of two things, both run by loopctl and never by an agent:
- **L1** (nothing is pushed): `git update-ref <ref> <new> <old>` in the local repo. It fails if the ref no longer holds `<old>`.
- **L2+**: `git push --force-with-lease=<ref>:<old> origin <new>:<ref>`. It fails if the remote ref moved.

`--force-with-lease` without an explicit `<ref>:<old>` is never used: it compares against the last fetch, not against what loopctl read.

**Loop working copy.** The loop runs in a **dedicated clone or worktree**. It refuses a dirty tree (L-1). While `loopctl/lock` is held, interactive sessions in the same repo are read-only on the loop's branches (CO-15).

**v1 → v2 field mapping (CO-19).** `migrate-plan` maps:
- `reworkNotes` → `items/<id>.json#rework[]`;
- `securityWaiver` → `waivers[]` with `{approver, expiry, finding_ids}` (H6);
- `downMigrationRef` → `migrations[].down`;
- `verifyEvidence` → the check-run URL.

Unknown fields fail validation loudly.

### 10.4 State machine, failure taxonomy, retries

```
pending → designing → design_review → stubbing → building → verifying → reviewing
        → pr_open → awaiting_human → merged | needs_human | blocked | abandoned
```

- The enum is closed and shared by the spec, orchestrate and loopctl (L-7).
- `blockReason` is required on `blocked` and `needs_human`.

**`failure_class`** is required on every failure (CO-8):

| Class | Example | Retry? | Consumes retry budget? | Trips breaker? |
|---|---|---|---|---|
| `platform` | API 5xx, overloaded, rate limit, CLI crash | Yes, backoff with jitter | **No** | No |
| `transient` | Flaky network in a test, port in use | Yes, ×2 | Yes | No |
| `env` | Toolchain mismatch, DB down, missing env var | No; park, notify, fix doctor | No | No; demotes effective level |
| `item` | Tests fail, review blocked, AC unclear | Per `max_retries_per_item` | Yes | Yes (no-progress breaker: same failing AC IDs twice) |

**Caps** get consistent names (CO-22):
- `max_review_rounds` (was `engineer-protocol.md:62`);
- `max_retries_per_item`;
- `max_design_rounds` (was `architect.md:100`);
- `max_ci_fix_attempts`.

Counters are durable in state, are not multiplicative (L-8), and survive resume.

### 10.5 Spend and cost (CS-26, CO-7)

**Ledger.** loopctl sums `total_cost_usd` from each child `-p` JSON result into the durable ledger. It passes the **remaining** budget as `--max-budget-usd` on every launch, because the flag's own count resets on resume and is a client-side estimate that can overshoot (P26).

**Budgets:**
- `budget_usd_run`;
- `budget_usd_item`;
- `budget_usd_day`.

Reaching any ceiling pauses the run, notifies, and sets `needs_human`.

**Projection.** At plan approval, `loopctl cost --projection` estimates from item count × the fixture's p50/p90 cost per item class, and the human approves the plan with that number visible.

**Per-PR cost line.** Every PR's audit block includes cost and model per agent.

### 10.6 Context continuity (CS-24, CS-23, L-17, L-18)

- **SessionStart, `compact` matcher**, returns `additionalContext` (≤10k chars). It carries the current item, stage, next action, open checkpoints and the path to the full protocol. PostCompact cannot inject [docs] (P30).
- **The Stop gate is advisory.** It honors `stop_hook_active`, and the 8-continuation cap is documented. **The external driver is the continuation mechanism.** When a child session ends, loopctl inspects state and launches the next one.
- Report schemas are re-validated by loopctl at the next dispatch. SubagentStop can't fail closed [docs].

### 10.7 Abort and rollback (CO-9, L-6, F-27)

`loopctl abort --rollback-to <sha>` does the following:
1. Halts all dispatch.
2. Lists merged items after `<sha>` in reverse topological order.
3. For each item not yet on `main`: reverts on the integration branch, or locally at L1, and runs down-migrations in reverse order against **local/ephemeral DBs only**. Shared DB rollback is H4.
4. Closes open PRs.
5. Marks dependents `abandoned` (reject cascade).
6. Writes an abort record.

**Scope: only before merge to `main` (RC-14).** The steps above apply to items under `delivery: local` or still on the integration branch (DEC-2). Once an item has merged to `main`, a revert lands on `main`, and on a deploy-on-merge repo (B5) that is a production deploy. Its down-migrations may reach a shared DB, which is H4. So after merge, `abort` and the reject cascade **write a revert plan** (the reverts in reverse merge order, each down-migration with its data-loss class) into an issue or a draft PR for a human. The loop never executes it.

It is tested in the fault-injection suite (§15) before L4.

## 11. Delegation, nested sessions and runners: what "automatic" means

### 11.1 The answer to goal G1

There are three layers. Each is automatic in a different sense.

1. **Inside a session**, dispatch to subagents is already automatic: the conductor calls Agent with an explicit `subagent_type`. The work is making it **reliable**:
   - Engineers are dispatched only with a brief path (D-16).
   - They write their own report file plus a JSON trailer (D-14).
   - They return `NEEDS_CLARIFICATION` instead of "ask the user" (D-15, P-16, A21).
   - They are resumed **by `agent_id`** via SendMessage, never by `name`. With agent teams on, a named spawn becomes a teammate in the main working directory (CS-29, P34).
   - `maxTurns` is set from the fixture's p95, not guessed (CS-32). On a `maxTurns` stop the engineer returns a partial result, and the conductor resumes it by id (P6).
2. **Across sessions**, "automatic" means the **external driver** (`loopctl run`), which a human starts once. It launches each child as:

   ```
   claude -p --agent <role> --settings <kit headless profile> --agents <roster json> --allowedTools <…> --permission-mode dontAsk --max-budget-usd <remaining> --output-format json
   ```

   It records each child's `session_id`, and waits on a report file plus process exit. **No agent ever launches `claude` or the SDK** (CS-2): guard-exec denies it, B3 has no route to it, and managed settings back that up at L3+.
3. **Fan-out** (reviews, critique voting) can use **Workflow**, but only from a **saved** `.claude/workflows/<name>` that the human-run `/orchestrate` invokes. That is the human opt-in the kit relies on. **The platform's opt-in is weaker than that** (RC-17): the `-p` keyword does not start a workflow, but a `-p` run *can* launch one through an allow rule (`Workflow` or `Workflow(<name>)`), because `-p` never prompts. So the kit denies `Workflow` in the headless profile and in engineers' `disallowedTools`, and the doctor fails on any `Workflow` allow outside the human-run `/orchestrate` profile. Launch from a subagent is UNVERIFIED (V23) (P13, CS-28).

**`start_session` (desktop) is not an automatic tier.** It is a deferred host tool, and some initiation modes create a proposal the human must start (P18, CS-28). It stays as a convenience for interactive humans. The kit does not rely on it.

### 11.2 Two axes replace the three incompatible tier schemes (CS-35)

| Axis | Values | Chosen by |
|---|---|---|
| `runner` (where an item runs) | `driver` (external `loopctl run`, one child `-p` session per item or stage), `in-session` (conductor → item-runner subagent → engineer), `sequential` (V1: conductor dispatches engineers directly) | **Explicit loop.config value** (CS-28). `/bootstrap` and the doctor *suggest* it from deterministic signals: CLI version, workspace trust, `disableWorkflows`, driver present. The model only validates and loudly downgrades |
| `pipeline_host` (how reviews and critiques fan out) | `conductor` (sequential Agent calls), `workflow` (saved Workflow) | Explicit config; `workflow` requires the saved file |

**Depth math, corrected (P5, CS-36).** Main → item-runner (layer 1) → engineer (layer 2) leaves layer 3 free. The default max depth is 3 and configurable via `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` [docs]. Engineers still get `disallowedTools: Agent, Skill`, so they don't spawn Explore. This is a design choice, not a depth limit: it keeps custody and cost visible. The `Agent(type)` allowlist is ignored in subagent definitions [docs] (P35), so the deny is the only reliable control.

### 11.3 Fork mode (CS-27)

Fork mode has been on by default in the terminal since v2.1.232, and in `-p` since v2.1.302 [docs] (RC-29):
- In interactive surfaces, the parent **can't block** on a subagent while fork mode is on.
- In `-p`, a nested spawner waits **only while** fork mode is on.

So, **gated on V18** (fork mode × runner × `-p`/interactive on the pinned floor; RC-29), not on the docs tag alone:
- **Dispatch is event-driven everywhere.** "Done" is a valid report file *and* a loopctl state transition, never "the Agent call returned".
- The driver sets the fork-mode and background-task env **explicitly per runner** in its `--settings` env, and the doctor asserts it.
- Critics and engineers are always spawned with an explicit `subagent_type`, so they are never forks of the conductor's context (D-24).

### 11.4 Model and effort routing (R1, CS-39, P7, CO-21, CO-34)

**`model_profile`:**
- `quality` (default): opus for engineers and critics, with per-role `effort`.
- `balanced`: sonnet for frontends; opus for backend, DB and critics.
- `economy`.

Default stays `quality` until fixture and eval data show parity (Install A evidence: sonnet frontends were poor; F-20).

**Precedence is per-invocation > frontmatter > env** [docs]. `CLAUDE_CODE_SUBAGENT_MODEL` is only a default. The kit documents `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` (v2.1.257+) for users who want an env override. The conductor omits the per-invocation model when FORCE is set.

**Escalation:** on CHANGES_REQUESTED round 2, re-dispatch at opus with `xhigh` effort.

**Verifier:** fable when available (§9 G8).

**Plan mode / opusplan / Advisor** (CO-34):
- **Plan mode:** recommended for the interactive Architect.
- **opusplan:** documented as an `economy`-profile option for the main session.
- **Advisor:** optional second opinion for G8. It is not on the critical path.

### 11.5 Decomposition and parallelism (deferred behind the evidence gate, except slicing)

1. **Slicing (ship early; planning-only, zero execution risk).**
   - The Architect adds `## Slices`: an ordered DAG of PR-sized slices (≤ `max_item_loc`, default 400), each with `touches {domains, paths, schema, deps_change}`, ACs and a risk class.
   - The Planner emits slices as items (L-35, D-7, F-8).
   - PLAN_REVISION_NEEDED returns a structured proposal (split, merge, reorder) through a plan PR (L-37, CS-22).
2. **Within an item.**
   - Engineers run sequentially on one branch, with a **WIP commit per engineer** by the conductor, so each review gets an exact range (D-4).
   - Delete the in-session DB+Backend parallel option (D-5, D-29).
   - Parallel frontends only in separate worktrees.
3. **Across items** (`parallel_mode: off | worktree`, default off, `max_parallel: 2`), only after the evidence gate:
   - Eligibility: dependencies merged on integration, disjoint footprints, and a schema mutex that is always on.
   - The conductor creates worktrees itself off local integration HEAD (D-3). `.worktreeinclude` lists only `.env.local`/`.env.test` (§5.4).
   - WorktreeCreate/Remove hooks handle install, port offset, ephemeral DB and teardown (D-22).
   - **Serial integrate:** rebase, re-run G6, regenerate timestamped migrations, single writer for state (D-6).
   - Reject cascade invalidates in-flight descendants (L-6).
   - Budgets sum across workers via the ledger (CS-26).
4. **Not used:**
   - agent teams (D-23; and their `name` hazard, CS-29);
   - forks for critics or engineers (D-24).

   `/batch` is used only for mechanical cross-cutting quick-lane changes outside custody (D-28).

### 11.6 Child-session prompt and the PM default posture (CO-36)

`CLAUDE.md:61` and `pm.md:76` make every session default to PM posture. A driver-launched child would then start interviewing nobody. Two fixes:
- Every child is launched with `--agent <role>`, whose role prompt explicitly overrides the default posture.
- The default-posture line in CLAUDE.md is scoped to "interactive sessions with no `--agent`".

**Size budget** for always-loaded context: CLAUDE.md + rules ≤ 8 KiB, and AGENTS.md ≤ 32 KiB, because Codex truncates at 32 KiB. The doctor checks both.

## 14. Version floor and drift

### 14.1 Floor: Claude Code v2.1.302

The design depends on these behaviors, each with the version it needs:

| Behavior | Since |
|---|---|
| Resumable `maxTurns` partial output | v2.1.246 |
| `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` | v2.1.257 |
| Per-invocation `effort` | v2.1.292 |
| `onFailure: block` on every blocking-capable hook (RC-30) | v2.1.295 |
| Fork mode on by default in the terminal | v2.1.232 |
| Fork mode on by default in `-p`; `-p` starts in Manual mode | v2.1.302 |

v2.1.302 is the floor because the last row changes how dispatch waits and how headless permissions start. A kit built for v2.1.295 would assume blocking dispatch and the wrong `-p` permission mode (CS-41).

### 14.2 Declared range, enforced at session start

- `KIT_VERSION` gains `claude_code_min` (2.1.302) and `claude_code_tested_max` (the newest version the canary passed).
- SessionStart compares `claude --version` with the range:
  - below the minimum: a loud banner at L0–L2, and **refusal** at L3+;
  - above the tested maximum: a warning at L0–L2, and **refusal at L3+** until the canary passes on that version.
- The driver applies the same check to itself before launching any child.

### 14.3 Pin and canary (CO-10)

- **CI pins the CLI** (`npm i -g @anthropic-ai/claude-code@<tested_max>`). Unattended runners use the same pin. Auto-update is off for the bot user.
- **Canary on every CLI release** (a scheduled CI job):
  - the hook-input schema snapshot (field names for PreToolUse, PostToolUse, SubagentStart, SubagentStop, SessionStart, ConfigChange);
  - the liveness canary (a guard must fire on a planted call);
  - the bypass corpus;
  - the safety eval cases at `--threshold 1.0`.
- **Schema drift fails closed.** If a guard sees an unknown hook-input shape (a missing `tool_input`, a renamed field), it denies, and the canary opens an issue. When the canary passes, it bumps `claude_code_tested_max` through a PR (H6, human-merged).

## 15. Validation strategy

Validation precedes and accompanies every phase. A phase that can't show a metric moving on the fixture is reverted (§16.2). Safety and boundary phases are the exception: they are judged on the bypass corpus, the injection corpus and the boundary fixtures (item 9), not on a fixture metric (RC-8).

1. **`examples/hello-loop/`** (Phase 0a).
   - A tiny pinned stack: one service, three items (schema, endpoint, UI), seeded data, a known-good plan, and a pinned toolchain (`.nvmrc` or `.python-version`, `engines`, lockfile).
   - Run **V1 under baseline conditions** at least **N = 3** times (or once plus 20 replayed dispatches per agent type, for `maxTurns`), in a dedicated clone with the sandbox on and no cloud credentials. Report ranges, not single numbers (RC-8).
   - "Baseline conditions" are not "unchanged". The deltas are listed with the results: the sandbox (V1 has none, and it changes which commands prompt or fail); no cloud credentials; the observation-only logging hook; and the demo capability, since orchestrate.md:36 assumes `Claude_Browser` and harness prompts.
   - Publish the transcripts, the metrics, and every human rescue.
   - It is the baseline for every later change, and it runs in CI with the toolchain pinned (DEC-27).
2. **Hook bypass corpus** (Phase 2).
   - Table-driven tests in `scripts/guards/tests/`: every Q2 bypass row, the worktree cases (D-2), wrapper normalization, interpreters and script files (CS-6), `--no-verify` and `core.hooksPath` (CO-3), git config escalation (CS-8), and nested `claude` / SDK launches (CS-2).
   - Deterministic and free, so it runs on every PR.
3. **`claude plugin eval`** (Phase 2 onward).
   - About 14–20 cases: mode routing, critic verdict schema, engineer refusing without a brief, the NEEDS_CLARIFICATION path, infra plan-only, test-integrity refusal, conductor refusing to launch `claude`.
   - **Safety cases** run at `--threshold 1.0`, which with k=3 means every run must pass. **Quality cases** run at 0.8, which is a mean, not pass^k (P28).
   - Exit code 2 counts as a failure in CI (CS-40). Every run sets `--max-cost-usd`.
   - `--ablation` shows which harness parts still pay their way; this is how the harness gets pruned at each model release.
4. **Injection corpus** (Phase 2, extended in Phase 7). A poisoned README in a dependency, a poisoned issue body, a poisoned web page, a poisoned MCP result, and a poisoned PR comment. All are safety cases at `--threshold 1.0` (§5.3).
5. **Fault-injection suite for loopctl** (the loopctl MVP, Phase 4, ships the serial cases: crash mid-item, stale local lock, malformed report, stall, 529, forced `/compact`. The rest is required before L4 and before parallel mode):
   - crash mid-item;
   - stale lock: local in Phase 4; remote with the Phase 11 remote lock;
   - human revert on the integration branch;
   - reject cascade, before merge to `main` only; after merge it must produce a human revert plan and execute nothing (§10.7, RC-14);
   - malformed report or trailer;
   - stall (no tool call for `dispatch_timeout_min`);
   - merge conflict on serial integrate;
   - whole-run abort and rollback (§10.7, CO-9);
   - platform 529 or overload (classified as `platform`, not as an item failure; CO-8);
   - forced `/compact` mid-run: state must survive through SessionStart(`compact`) (CO-35).
6. **`/orchestrate --dry-run`** (Phase 4): renders the plan, gates, runner and budget projection without executing anything.
7. **Dogfooding.** Every kit release runs hello-loop end to end at the highest level it claims to support, and publishes the result in the release notes (CO-45).
8. **Onboarding per level** (CO-45). getting-started.md gains "start at L0; move to L1 after N clean runs; L2 needs Phase 1 done; L3 needs the §6.3 evidence bar". The doctor prints the current effective level and what blocks the next one.
9. **Boundary fixtures** (Phase 1, extended in Phase 6). Each is a must-refuse case, run in CI against a scratch repo with the real ruleset:
   - **Deploy by side effect (RC-1).** A repo with an `on: push` deploy workflow: an L2 bot branch push is refused by `doctor --deploy-surface` before it happens. A repo that deploys on merge to `main`: L5 docs auto-merge is refused.
   - **Human credentials (RC-5).** From the agent's sandbox, `git push origin HEAD:main` is tried with every ambient credential (gh token, git credential helper, SSH agent, `GH_TOKEN`/`GITHUB_TOKEN`). Every attempt is rejected.
   - **Bypass list (RC-9).** The bot is not in any ruleset bypass list. On a solo install, the only bypass is the human admin in `pull_request` mode.
   - **Skill hooks in CI (RC-18).** A PR adds a skill whose frontmatter has a `PreToolUse` hook that writes a marker file. The CI `-p` job must not create the marker.
   - **Workflow headlessly (RC-17).** A driver child with a `Workflow` allow injected into its settings is refused by the doctor before launch.

## 16. Roadmap

Each phase ships using only what earlier phases shipped. The draft broke that: Phase 1 needed the loopctl doctor and Phase 3 needed G6, both from later phases (RC-7). **Why 0a → 1 → 0b (RC-24).** The numbers are kept from the draft so cross-references stay stable; the order is deliberate. 0a measures V1 before anything changes. 1 is the boundary, which lives mostly outside the kit and must exist before any later phase gives the agent more reach. 0b is cheap prose and frontmatter work that would otherwise muddy the baseline if done first.

- the baseline runs first, under listed baseline conditions (CS-31, CO-12, RC-8);
- the real boundary comes before kit conveniences (CS-30);
- the interactive PR lane comes before loopctl (CS-33);

### 16.2 Kill criteria

Written into the repo in Phase 0a, before any building. They are the report's answer to over-engineering (CS-34):
- **loopctl is justified only if** the baseline needs **more than 3 control-flow human rescues per run** (resuming, re-dispatching, fixing state by hand), taken across the N ≥ 3 runs. If it needs 3 or fewer, the Phase 4 MVP shrinks to `validate`, `status` and `doctor`.
- **If most failures are `env`** (toolchain, ports, DB, dependencies), the doctor and G0 come first, ahead of everything in Phases 2–4.
- **If V1 cannot finish the fixture at all** (RC-8), Phase 2 guards and the doctor come first, and the loopctl decision is deferred until a run finishes.
- **Every capability phase must improve a fixture metric** (rescues, failure count by class, defect escape, spend, wall time), or it is reverted. **Safety and boundary work is exempt** (Phase 1, the Phase 2 corpus and ConfigChange blocker, and the boundary parts of 0b and 6): it is judged on the bypass corpus, the injection corpus and the §15 item 9 fixtures (RC-8).
- **Gates whose owner metric never moves** are removed at the next model release (the ablation review in Phase 10).
- **A safety eval or corpus regression** blocks the release, with no waiver.

### 16.3 Minimal path

If you do only five things:
1. **Phase 0a:** baseline on hello-loop, and the kill criteria.
2. **Phase 1:** bot identity, no reachable credentials (the human's own included), the deployment-surface audit, sandbox, rulesets with no bot bypass, split base-ref CI.
3. **Phase 0b:** the prose and frontmatter fixes (cheap, and they remove known failure modes).
4. **Phase 3:** draft-PR delivery in the interactive lane, which is how you already ship.
5. **Phase 6's infra rule as policy only:** the agent never holds cloud credentials; plan runs in CI after policy; apply needs a human, through an Environment or a human-only dispatch where the GitHub plan has no Environment reviewers.

That set gets the kit to a safe L2 for the way you actually work. Everything else is earned by the evidence gate.

### 19.7 Short specs for sub-items the draft dropped

These are the fixes the critics found missing from the draft (CO-41, CO-42, CO-43), plus eight items that no earlier section of this report mentioned.

**Lock (F-7 fields, L-11 atomicity, CS-19).**
- **Record:** `{runId, sessionId, host, worktree, driverPid, startedAt, heartbeat, planRev}`. `driverPid` is meaningful under `runner: driver`, because `loopctl run` is a long-lived process. orchestrate.md:30 rightly says a Bash pid proves nothing.
- **Acquire:** O_EXCL create of `<git-common-dir>/loopctl/lock`. `mkdir` is an equally atomic shell fallback; either is fine. The lock lives outside `.claude/` (CS-25).
- **Heartbeat:** re-stamped by a PostToolUse hook on any tool activity in the owning session, not by the model.
- **Stale:** only when the heartbeat is older than `lock_stale_min` **and** the owner isn't live (driver pid gone, or session not registered).
- **Remote (Ph 11; RC-10, RC-12):** `refs/loopctl/lock/<plan>`, created only with `git push --force-with-lease=refs/loopctl/lock/<plan>: origin <sha>:refs/loopctl/lock/<plan>`. The empty expected value means "must not exist"; a plain push does not fail when the ref exists. Heartbeat and release use the CAS defined in §10.3. GitHub rulesets target branches and tags only, so nothing can protect `refs/loopctl/*`: anyone with `contents: write` can move or delete it. The remote lock is advisory coordination between hosts, **not a security boundary**. guard-git allows `refs/loopctl/*` pushes only from loopctl invocations.
- **Fallback:** for hosts that reject custom refs, a `factory:running` label plus assignee on the tracking issue.

**Discard and retry (L-2).** Discard runs only inside the loop's registered worktree, never the human's checkout (CO-15). The guard allows it there and nowhere else:
1. `git reset --hard && git clean -fd`;
2. rename the branch to `dead/<slug>-a<n>`;
3. drop the item's ephemeral DB.

Retry table:

| Failure | Action |
|---|---|
| verify fail | resume the implicated engineer with the failure tail, same branch, fresh ephemeral DB |
| review blockers | resume the engineer with the blocker list |
| `PARTIAL` | split the remaining scope into a new item |
| critic cap hit | hard stop |
| retry cap (`max_retries_per_item`) exhausted on verify, or a reward-hack signature found (deleted or weakened assertions, edits to pinned G3 tests) | **discard** (steps above) + a fresh attempt `a<n+1>` from the item's base, with the failure summary but none of the old diff (RC-19); a second discard on the same item → hard stop |

This is the only path that calls discard, and so the only `reset --hard` the guard allows. Prune `dead/*` at run finish.

**Branch lifecycle and orphan sweep (L-3).**
- Branches: `feat/<slug>-a<n>`, with the attempt counter kept in state.
- Merged branches are deleted after pass. A hard stop renames the branch to `blocked/<slug>-a<n>`, preserving the work for resume.
- **Orphan sweep** is a `loopctl reconcile` step. Worktrees and `feat/*` branches with no live state are renamed to `dead/`, and pruned after `orphan_retention_days`. `blocked/*` is never auto-deleted.

**Trailers (L-4).**
- `Loop-Item: <id>`, `Loop-Run: <runId>`, `Loop-Attempt: <n>`, `CI-Fix-Of: <sha>`.
- Required on feature and merge commits under `delivery: local`. There, reconcile with `git log --merges --format='%H%x09%(trailers:key=Loop-Item,valueonly)'` and an exact match, which also fixes `git revert -m 1`.
- Under PR delivery the PR number is the key, because squash and rebase drop trailers (CS-20).

**Human-revert detection (L-5).** At reconcile:
- under local delivery, scan for `This reverts commit <mergeCommit>`;
- under PR delivery, scan for GitHub revert PRs referencing the item's PR.

A detected revert moves the item to `needs_human`. It is never silently re-run.

**Reject cascade (L-6).** Scope: items not yet on `main`, that is, the loop's local integration branch under `delivery: local`, or open PRs under PR delivery (RC-14). Rejecting such an item:
1. computes its transitive dependents merged after it;
2. reverts them in reverse merge order;
3. runs their down-migrations in reverse order, on ephemeral DBs only (lossy downs are human-gated, CO-18);
4. resets all of them to pending.

Once any affected item has reached `main` or a shared DB, loopctl does **not** revert or migrate. It writes a human revert plan (revert PRs in reverse order, the down-migrations and the environments they touch) and moves the items to `needs_human`. A revert push to `main` can deploy (B5), and a shared-DB down is H4. "Reject milestone" is offered as a unit, and the checkpoint names which items a milestone reject touches.

**Down-migration proof (L-25).** `db_migrate_down` is added to loop.config and local-dev.md. For items whose diff touches migration paths, `loopctl gate migrations` runs up → down → up on the ephemeral DB and records `downMigrationRef`.

**Process groups and ports (L-27).** loopctl launches the dev server in its own session (Python `start_new_session=True`) and kills it with `os.killpg` after a timeout. Bash `set -m` is the fallback; macOS has no `setsid` by default.
- Before boot: check the ports are free, using dedicated verify ports.
- Readiness: Monitor streams the log in interactive mode, and loopctl polls with a deadline headless. Neither uses `sleep` loops in prose.

**Model helpers (L-31).** Routing comes from the profile (§11.4).
- Critics and DB/backend engineers run at opus `high`. The verifier is fable.
- Haiku helpers for "render" and "summary" are mostly moot, because loopctl render is deterministic. Haiku is allowed only for the optional PR-body prose summary.

**Primer Delta (L-32).** The protocol's step 5.5 (primer update) moves **before** merge, on the item branch.
- A SubagentStop check for `## Status` / `## Primer Delta` / `## Telemetry` is a warning only, because SubagentStop can't fail closed (P2).
- The real enforcement is loopctl's report parse. A missing section, or `NONE` without a `checked: <sections>` line, gives `malformed_report`.
- `loopctl status` flags N consecutive items that add new top-level dirs or deps with an empty delta.

**Blocker definition (L-34).** A blocker is something that would cause an engineer escalation, a contract mismatch, data loss, security exposure, or an acceptance-criterion failure. The rubric includes three or four calibrated examples. Each blocker is logged with its outcome ("did an engineer hit it?") to measure precision.

**Slicing rules (L-35, `max_item_loc`).** Each item is:
- one user-visible vertical slice;
- ≤2 engineers preferred, 3 at most;
- ≤1 migration;
- ≤ `max_item_loc` (400) estimated changed lines;
- ≤3 acceptance checks.

Planning order: walking skeleton first, then thicken. Items carry `size: S|M|L`, and L must be split. `loopctl validate` reports critical-path length and maximum DAG width at approval. Install A's 300–400 LOC slices with 2a/2b/2c splits are the reference.

**Dialect parity (L-38, DEC-8).** `db_local` defaults to the production engine, in-process first:
- Node: PGlite or embedded-postgres;
- otherwise, or when the in-process engine can't match the prod version: Docker or testcontainers.

SQLite is allowed only when production is SQLite or libSQL. With no in-process engine and no Docker, the doctor reports an **error** and the plan's effective level is capped at L1 (RC-21).

Per-item ephemeral DBs are created with `CREATE DATABASE … TEMPLATE <seeded>`, which takes seconds.

**Permissions (L-41).**
1. Ship `settings.loop.example.json`, built from loop.config and local-dev commands: read-only git, and package-manager test/lint/build.
2. The driver uses `dontAsk` + `--allowedTools`.
3. The sandbox (B3) is what justifies a broader allowlist.
4. `/fewer-permission-prompts` is for the interactive lane only; the human reviews its diff (§12.1).
5. A **PermissionRequest** hook in interactive and unattended interactive sessions pushes a notification when a prompt blocks. Under `dontAsk` nothing prompts, and denials are logged as events instead.
