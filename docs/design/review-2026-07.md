**Method**: Four independent review passes over every file in the kit — (1) cross-document consistency/drift, (2) workflow completeness and failure paths, (3) mechanical correctness inside Claude Code (frontmatter, settings, hook — the hook was tested empirically by piping PreToolUse JSON), (4) onboarding and coverage gaps. Findings were deduplicated across passes; where two or more passes found the same issue independently, that is noted as a confidence signal. High-impact claims (hook behavior, LICENSE absence, orchestrate step ordering) were re-verified directly against the files before recording.

**Severity scale**: **HIGH** = breaks a run, dead-ends a user, or blocks adoption. **MED** = user must improvise or is silently misled. **LOW** = polish/hygiene.

## Cluster 1 — Loop runtime machinery

The loop's own moving parts. These are the findings that break or dead-end actual runs.

### 1.1 The kit's own git hook blocks the loop's own fail path — HIGH ✅ verified empirically

- **Files**: `.claude/hooks/guard-git.sh:41-42`, `.claude/commands/orchestrate.md` step 5, `docs/design/loop-engineering.md` §9.
- **Found independently by**: mechanics + workflow passes.
- Orchestrate step 5 Fail: "Still failing → **discard branch** + ephemeral DB, mark `blocked`." Design §9: "a *failed* item (never merged) = delete branch." Deleting an **unmerged** branch requires `git branch -D` (`-d` refuses). The hook blocks it unconditionally — `if sub == "branch" and ("-D" in args …)` — with **no branch-name check**, so the conductor's own feature branch is blocked too. Tested: `git branch -D feat/foo` → exit 2, "BLOCKED by guard-git."
- The hook header's claim that blocked ops "never conflict with the conductor's allowed set" is **false** for this path.
- **Scenario**: item fails verify twice → conductor cannot discard the branch → stale branch persists → when the item is later retried, "cut `feat/<slug>` off current main" fails because the branch exists. Same collision on crash-resume (reset `in_progress`→`pending` → restart needs a fresh branch).
- **Fix direction**: allowlist deletion of `feat/*` branches in the hook (keep blocking main/master/origin), or switch the documented fail path to `git branch -m` to a `dead/` namespace.

### 1.2 Merged migrations are never applied to the durable dev DB — HIGH

- **Files**: `.claude/commands/orchestrate.md` steps 3, 5, 7; `docs/design/loop-engineering.md` §8/§9.
- Verification runs only against the ephemeral copy ("copy the dev DB file to a temp path"); on pass the copy is **discarded** and the branch merges. **Nothing ever migrates `./.data/dev.db`.** Consequences: (a) the checkpoint auto-demo boots the app against the un-migrated durable DB — the just-merged feature's tables don't exist, so the demo route 500s; (b) every subsequent item's ephemeral DB is copied from that same stale dev.db, so all later verifies silently depend on the test harness auto-applying the full pending migration chain — an assumption stated nowhere.
- Related: §8 says the proven down-migration is "recorded for application against the durable DB at push/revert time" — **no field, file, or step says where it is recorded or who applies forward migrations** (not in the build-plan item schema, not in the loop.jsonl record shape).
- **Fix direction**: add an explicit "apply migrations to durable DB" step to the pass path (after merge, before demo), and add a `downMigrationRef` field to the build-plan item.

### 1.3 No specified way to un-block anything — every failure terminus is a dead-end — HIGH

- **Files**: `.claude/commands/orchestrate.md` (step 1: "`needs_review` / `blocked` are surfaced, **never auto-selected**"; hard-stop list), `docs/features/_templates/build-plan.md` ("State ownership: the **Orchestrator** owns `status`"), `.claude/commands/planner.md` (edits structure only).
- Every failure terminus — `blocked`, `budget_halted`, `contract_blocked`, `needs_provisioning`, `security_blocked`, breaker trip — leaves items the loop will never pick up again, and **no command, mode, or instruction anywhere resets a status**. The user hand-editing `build-plan.json` violates the kit's own state-ownership rule.
- Also unspecified: the security "block until resolved or **waived**" waiver mechanism (loop.config.md) does not exist anywhere; `DESIGN_DEVIATION` → "flag for Architect ratification" has no defined procedure (who, how, what happens if rejected after dependents merged).
- **Scenario**: user supplies the missing `STRIPE_KEY` after a `needs_provisioning` stop, re-runs `/orchestrate` → item still `blocked`, never auto-selected → immediate `DEADLOCK` on a plan that is actually fine. Every user hits this after their first failure.
- **Fix direction**: define an explicit unblock verb — e.g. a preamble step: "surface all non-`pending`/non-`done` items; for each, ask the user (or in unattended mode, apply documented rules) whether to reset to `pending` with `blockReason` cleared." Add a security-waiver field with required justification.

### 1.4 `needs_review` contradicts the pipeline order — checkpoint marks an already-merged item — HIGH ✅ verified in file

- **Files**: `.claude/commands/orchestrate.md` steps 5 and 7; `docs/features/_templates/build-plan.md` lifecycle diagram.
- Step 7: "At a discretionary checkpoint, **mark the paused item `needs_review`** before pausing … On resume, the `needs_review` item returns to `in_progress`/continues." But checkpoints run **after** step 5 already marked the item `done` and merged it. So: (a) `needs_review` overwrites `done`, breaking dependent eligibility (`eligible = every dependsOn item is done`); (b) "returns to `in_progress`" is meaningless for a finished, merged item; (c) if the session dies while paused, the merged item is stranded — JSON↔git reconciliation only inspects `done` items, so the merge is invisible.
- The build-plan template's lifecycle diagram shows `needs_review` branching from `verifying`, which contradicts orchestrate's actual sequencing — the two documents disagree about the state machine.
- **Scenario**: per-milestone checkpoint after F4 → user closes laptop → next session sees F4 `needs_review`, skips it → F5 (`dependsOn: F4`) ineligible → DEADLOCK with F4's code already on main.
- **Fix direction**: don't repurpose item status for pause bookkeeping. Keep the item `done`; record the checkpoint as a run-level flag (e.g. `checkpoint_pending` in the lock file or plan header).

### 1.5 No path for the user rejecting work at a checkpoint — HIGH

- **Files**: `.claude/commands/orchestrate.md` step 7; `docs/design/loop-engineering.md` §9.
- The checkpoint script has exactly one exit: "the loop proceeds." "This is wrong, redo it" has no owner — the item is already merged to local main. §9 names the revert mechanics ("`git revert` the code and run its proven down-migration") but never wires them to any actor, trigger, or mode. A redo also needs the item reset to `pending` (see 1.3).
- Demo **failure** (screenshot shows an error page) is not in the signal table — a broken demo either silently proceeds or the conductor improvises.
- **Fix direction**: specify checkpoint outcomes: *approve* (proceed), *reject* (conductor reverts merge + down-migration, resets item to `pending` with feedback attached), *stop* (pause run, item stays `done`). Add a `DEMO_FAILED` handling rule.

### 1.6 Run-scoped counters are not durable — the breaker resets on resume, reinstating the bug v3 fixed — MED

- **Files**: `docs/design/loop-engineering.md` §7 ("resets to 0 only when an item reaches `done` — *not* on human resume, so failures accumulate across resumes"); `.claude/commands/orchestrate.md` (breaker, `max_tool_calls_per_run`, `max_items_per_run`); loop.jsonl schema (per-item `tool_calls` only).
- The breaker counter, run tool-call tally, and items-this-run count live **nowhere on disk**, and no resume step says to re-derive them from `loop.jsonl`. A new session starts all run counters at 0 — silently reinstating the "logically dead breaker" defect that v3's revision explicitly claims to have fixed. Whether a "run" even spans resumes is undefined.
- **Fix direction**: add a preamble step: re-derive breaker and run tallies from `loop.jsonl` records since the last `done` (or last run boundary marker); write a run-start record so boundaries are explicit.

### 1.7 The run lock cannot work as specified — MED

- **File**: `.claude/commands/orchestrate.md` preamble step 1 ("pid + ISO timestamp … stale if its pid is not alive (`kill -0 <pid>` fails) **or** its timestamp is older than 30 minutes").
- (a) *Which* pid is unspecified — each Bash call is a fresh shell, so a lock recording `$$` is always stale one call later; the lock is a no-op against a concurrent session. (b) The **OR** means any run longer than 30 minutes (i.e., every real run) presents as stale with no heartbeat/refresh step specified — a second session may legitimately reclaim a live run → two conductors writing `build-plan.json`.
- **Fix direction**: drop the pid; use timestamp-only with a mandatory heartbeat touch in the per-item loop (e.g. re-stamp at each step 6), and raise the staleness window above the longest plausible single-item time.

### 1.8 Crash windows in the pass path — merge and JSON write are not atomic — MED

- **File**: `.claude/commands/orchestrate.md` step 5 pass path vs preamble reconciliation.
- Sequence: record `verifyEvidence` → mark `done` → commit → merge → store `mergeCommit`. Die between merge and the JSON write → the item resets `pending` on resume and gets **rebuilt on top of its own merged code**. Die between "mark `done`" and "store `mergeCommit`" → reconciliation must handle a `done` item with `mergeCommit: null`, a case with no defined behavior.
- **Fix direction**: reorder — write `done` + `mergeCommit` in one JSON update *after* the merge; extend reconciliation to treat "branch merged but item pending" (detectable via `git log --grep <itemId>` or branch presence in main's history) as "mark done," and "`done` with null `mergeCommit`" as "recover hash from git log."

### 1.9 `verify_run` semantics are unspecified for a non-terminating command — MED

- **Files**: `.claude/loop.config.md` (`verify_run: <command>` "e.g. `pnpm dev` + a preview assertion"), `.claude/commands/orchestrate.md` step 5 (`runExit`), `.claude/context/local-dev.md` (all placeholders).
- `pnpm dev` never exits, yet the gate requires captured exit codes and a `runExit`. The boot → probe-demo-route → record → kill harness is nowhere specified, and `local-dev.md` — the file that should carry it — ships as placeholder comments with **no example anywhere in the kit** (see 4.8). Every adopter must invent the glue that the falsifiability of the whole gate rests on.
- **Fix direction**: specify the harness pattern once in `local-dev.md`'s template (start server in background → poll route with timeout → curl assertion → capture code → kill) and ship a filled example.

### 1.10 Loop handoffs reference files that don't exist in loop mode — MED

- **Files**: `.claude/agents/design-critic.md` (Inputs: "Path to `docs/features/<slug>/requirements.md`"; Required Reading #2) vs `.claude/commands/pm.md:90` ("no `requirements.md` round-trip needed in the loop"); `docs/features/_templates/brief.md` Required Reading #4 (`requirements.md`) and its Iteration-2 addendum naming the `code-review:code-review` skill (which the loop explicitly does not use).
- **Found independently by**: consistency + workflow passes.
- In an `/orchestrate` run, the design-critic's declared **mandatory** input file does not exist; engineers' required reading names it too. Whether the conductor should synthesize the file, pass inline text, or the critic should skip it is unspecified — each improvisation weakens the "reuse the actual critic, not paraphrases" principle. Also unspecified: whether the autonomous conductor writes briefs to `docs/features/<slug>/briefs/` at all (code-reviewer permits "in-message brief text"; design-critic has no such alternative).
- **Fix direction**: add a loop-mode input contract to design-critic and the brief template: "in loop mode, requirements arrive inline in the dispatch prompt; treat as equivalent."

### 1.11 `max_retries_per_item` is consumed by three different counters — MED-LOW

- **Files**: `.claude/loop.config.md` ("within-item **verify** retries") vs `.claude/commands/orchestrate.md` (code-review re-dispatch cap; `PARTIAL` split-re-dispatch cap; verify-fail pipeline retry cap).
- One config value caps three loops with no statement whether they share a counter. Worst-case reading: each of 2 pipeline retries contains its own 2 review re-dispatches and 2 PARTIAL splits — ~3× the budget the user thinks they configured (bounded only by `max_tool_calls_per_item`).
- **Fix direction**: one sentence in loop.config.md declaring shared vs independent counters (recommend: independent, and say so).

### 1.12 No in-loop primer/CLAUDE.md maintenance — the autonomous Architect's inputs go stale — MED

- **Files**: `.claude/commands/orchestrate.md` per-item pipeline (no primer step) vs `.claude/commands/architect.md` Phase C and `.claude/commands/tech-lead.md` A.8.5 (interactive-only primer updates).
- The interactive flow's anti-drift mechanism ("Drift between primers and reality is the enemy") has no counterpart in the loop — precisely where the autonomous Architect designs "from the primers." Item 20's design is made from item-1-era primers. Additionally, nothing updates the sentinel-laden `CLAUDE.md` tech-stack table after the Planner's Phase-2 decisions, so the preamble's sentinel grep can keep downgrading autonomy forever on a greenfield run.
- **Fix direction**: add a primer-delta step to the pass path (same contract as A.8.5), and make the greenfield baseline item's definition-of-done include stamping CLAUDE.md's stack table.

### 1.13 `ESCALATION_NEEDED` leaves item status undefined → re-select loop across resumes — MED

- **File**: `.claude/commands/orchestrate.md` ("immediate hard-stop; set `blockReason` = signal" — status never set) + resume rule ("reset `in_progress` → `pending`").
- If the item stays `in_progress` at the hard-stop, every resume resets it to `pending`, re-selects it, re-runs the full pipeline, and hits the identical escalation — burning a pipeline's tool calls per resume, with no accumulating counter (`ESCALATION_NEEDED` explicitly "does not increment the breaker").
- **Fix direction**: set status `blocked` (with `blockReason`) at every hard-stop, then rely on the unblock verb from 1.3.

### 1.14 Hook bypasses via ordinary command forms — MED ✅ verified empirically

- **File**: `.claude/hooks/guard-git.sh`.
- Verified bypasses (exit 0, not blocked): **newline-separated commands** (`echo hi\ngit push` — the most common way models chain Bash), `FOO=1 git push` (env prefix), `command git push`, `echo hi&&git push` (no spaces), `(git push)` (subshell — shlex tokenizes `(git` so the OPS-set check misses), `echo git push | sh`. Allow-on-uncertainty is the documented design, but newline and subshell are *ordinary* forms, not adversarial ones — the backstop is porous for its primary use case.
- **Fix direction**: split the input on newlines before tokenizing; strip leading env-assignments and `command`; treat `(` prefix by stripping it. (Perfection isn't the bar — the header says so — but these four are cheap.)

### 1.15 Hook fails open when python3 is absent — LOW

- **File**: `.claude/hooks/guard-git.sh`. `python3` missing → exit 127 → PreToolUse treats as non-blocking → command runs. Consistent with allow-on-uncertainty, but the guard silently becomes a no-op with no signal to the user. **Fix direction**: `command -v python3 >/dev/null || { echo "guard-git: python3 missing — guard inactive" >&2; exit 0; }` so it at least announces itself. Document python3 in prerequisites (5.4).

### 1.16 loop.config promises a missing-file refusal that orchestrate never implements — LOW

- **Files**: `.claude/loop.config.md:5` ("If this file is missing, `/orchestrate` refuses to start") vs `.claude/commands/orchestrate.md` preamble, which handles only *placeholder* values (gate 4b), never file absence. **Fix direction**: add the file-exists check to preamble gate 4b.

### 2.4 "PM is the default mode" is mechanically inert — MED

### 2.5 On-main Edit/Write hook is referenced as if it ships — it doesn't; interactive lanes have no branch discipline — MED

## Cluster 3 — The greenfield deferral is not a safe deferral

Design §14 defers a dedicated bootstrap mode, claiming "the greenfield baseline item is the stopgap." The review's verdict: the other §14 deferrals are safe (parallelism is enforced-sequential; contract registry, cost analytics, cloud deploy degrade gracefully) — **this one is not**. Three concrete holes, on the path getting-started.md aims at the least-technical audience.

### 3.1 No git repo exists in an empty folder — HIGH

- No preamble step checks for or performs `git init` + initial commit. Step 3 "cut `feat/<slug>` off current main" fails immediately; the lock and reconciliation steps also assume git. Nothing in any doc says "run `git init` first" — the precondition is undocumented even for the interactive lanes.

### 3.2 Verify-command chicken-and-egg — HIGH

- The preamble hard-stops unless `verify_tests`/`verify_run`/`db_ephemeral` are real commands — but for greenfield those commands describe an app the baseline item hasn't created yet. The user must pre-commit to a guess; a wrong guess only surfaces as an F1 verify failure that burns retries. getting-started's "first run only" workaround makes the hard-stop a designed-in first-run failure, and **no owner is assigned** for filling loop.config (Planner? first item? user?).

### 3.3 No engineer owns scaffolding — HIGH

- `.claude/commands/tech-lead.md` A.2 maps design sections (Data Model / API Surface / Frontend Impact / infra) to engineers; empty scopes are explicitly "no dispatch." The baseline item's real work — repo layout, package manifests, test harness, lint config — matches **no row**. Either nobody builds the skeleton or the conductor improvises outside every specified role.
- **Fix direction (3.1–3.3)**: these three plus 1.12's CLAUDE.md-stamping belong in the planned bootstrap mode's definition — design it to (a) `git init` + initial commit, (b) fill loop.config as a Planner output rather than a user precondition, (c) give the baseline item an explicit owner (backend-engineer with a scaffold brief, or a dedicated scaffold role).

### 3.4 Roster shape assumes web SaaS; adaptation guidance has holes — MED

- Partial mitigations exist (README Tuning: delete admin/infra, duplicate app for mobile; choosing-your-stack: mobile "patterns transfer," API-only "delete the frontend agents"). Missing: CLI tools, desktop apps, data/ML pipelines, games — no guidance; what happens to the Backend→frontend dispatch-ordering gate (§6.1) when no frontend agent exists is never stated; "delete the frontend agents" leaves `shared-frontend.md` and the api-contract-centric templates dangling; mobile is told "duplicate app-engineer.md" but the loop's auto-demo (browser screenshot of a route) has **no mobile analogue** — unaddressed.

### 3.5 Checkpoint contract assumes git fluency the beginner docs disclaim — MED

## Cluster 4 — Adoption / install path

The "drop `.claude/` into any project" story, walked as (a) an existing-codebase owner and (b) an empty-folder beginner. The greenfield-beginner path is the best-documented; the existing-codebase small team — arguably the larger real audience — has the thinnest coverage.

### 4.1 `cp -r .claude` collides with an existing `.claude/` directory — HIGH

- **Files**: `README.md` Quick Start step 1, `docs/getting-started.md` Step 1.
- Any project that has used Claude Code already has `.claude/`. The prescribed copy nests (`.claude/.claude/`) or silently merges — clobbering the adopter's `settings.json` (permissions, hooks), `CLAUDE.md`, and any existing agents/commands. No merge guidance, no backup warning, no note that the kit's settings.json replaces theirs with an empty allowlist + a Bash PreToolUse hook. Every existing Claude Code user hits this at minute one.

### 4.2 No brownfield primer-generation path — HIGH

- **File**: `README.md` step 2 (the only guidance: interview-style "Help me fill in CLAUDE.md — ask me questions," "maybe an hour total").
- For a large legacy repo the information is in the code, not the owner's head. There is no "run Claude over the codebase to generate the primers" recipe, no partial-fill guidance — the Endpoint Catalog / Table Catalog sections in `backend.md`/`database.md` implicitly demand *every* endpoint and *every* table, with no advice on scoping, sampling, or pointing at a schema file instead. This is the kit's primary "existing project" audience, in their first hour.
- **Fix direction**: a documented bootstrap prompt/recipe ("generate each primer from the codebase; catalogs may reference source-of-truth files instead of enumerating").

### 4.3 `cp -r docs` dumps kit internals into the host project — MED

- Copying `docs/` brings the templates (needed) **plus** `design/loop-engineering.md`, `assets/`, `getting-started.md`, `choosing-your-stack.md` — kit documentation, not project documentation — and merges into any existing `docs/`. Note `orchestrate.md` cites "Authoritative spec: `docs/design/loop-engineering.md`" (3×, incl. "§6.1") and planner.md needs `_templates/build-plan.md` + `choosing-your-stack.md` — so parts of docs/ are **load-bearing at runtime**, but nothing tells the adopter which files are required vs. baggage. A `.claude/`-only adopter gets dangling "authoritative spec" references and modes that improvise the formats the templates were meant to pin.
- **Fix direction**: move runtime-load-bearing content under `.claude/` (or a `.claude/kit/` docs subdir), leaving `docs/` purely human-facing; or ship an explicit manifest of required files.

### 4.4 The kit's `.gitignore` never reaches the host project; loop artifacts land in git — MED

- **Found independently by**: three passes.
- Install copies only `.claude/` and `docs/` — never the `.gitignore`. README's claim that `metrics.jsonl` is "auto-created, gitignored" is false in the adopter's repo. Additionally, even the kit's own `.gitignore` misses `.claude/orchestrate.lock` and `.claude/loop.jsonl` (which includes full verify-output tails) while covering `metrics.jsonl` — inconsistent treatment of the two telemetry files. Commit-or-ignore guidance for `build-plan.json`/`BUILD_PLAN.md` is absent.
- **Fix direction**: add loop artifacts to `.gitignore`; add an install step "append these lines to your project's .gitignore"; document build-plan.json as commit-intended (it's durable state).

### 4.5 Stranded cross-links after the prescribed copy — LOW

- `GLOSSARY.md` and `README.md` live at kit root; `getting-started.md` and `choosing-your-stack.md` link `../GLOSSARY.md` / `../README.md`. After the copy those links dangle in the host project (or resolve to the *host's* README). getting-started also points users at `examples/` — which the copy never brings and which vanishes with `/tmp/ai-team`.

### 4.6 Undeclared dependencies — MED-HIGH in aggregate

- **README Prerequisites lists only "Claude Code CLI installed."** Actually assumed:
  - **context7 MCP** — hard-wired into all 8 agents' `tools:` frontmatter and mandated by engineer-protocol §9 ("Don't trust training-data memory"). Moreover the wired names (`mcp__plugin_context7_context7__*`) are **install-specific**: correct for a plugin install named `context7`; a plain MCP-server install exposes `mcp__context7__*`, so the frontmatter allowlist silently strips the capability while §9 still mandates it. Fails soft, quality bar becomes unfulfillable.
  - **`superpowers:brainstorming` skill** — invoked by `pm.md:28` and `planner.md:29`; no install note, no fallback.
  - **`code-review:code-review` skill** — the interactive Tech Lead's review mechanism (fallback exists at tech-lead.md ~121 but the dependency is never surfaced).
  - **`Claude_Preview` MCP / `preview_screenshot` / `PushNotification`** — named in orchestrate preamble step 5/§8a. In current Claude Code the browser preview is `Claude_Browser` (`mcp__Claude_Browser__preview_start`), screenshots are `computer {action:"screenshot"}`, and no `PushNotification` tool exists — so the "preferred" path can never trigger and every run silently uses the text fallback.
  - **python3 on PATH** — guard-git.sh dependency (fails open; see 1.15).
  - **Claude Code feature floor** — agents frontmatter, PreToolUse hooks with `$CLAUDE_PROJECT_DIR`, Skill tool; no minimum version stated.
- **Fix direction**: a real Prerequisites section (required / recommended / optional-with-fallback), and update orchestrate's tool names to current Claude Code reality while keeping the capability-probe framing.

### 4.7 loop.config filling is hardest exactly where the kit is silent — MED

- `db_ephemeral` is genuinely hard for brownfield Postgres/MySQL — the kit's whole answer is a one-line comment ("template clone or disposable container"); no worked Postgres example exists anywhere. `verify_run` has no concrete example value. A brownfield project with **no test suite** has no documented path at all — `verify_tests` must "collect >0 tests," so the loop is unusable until tests exist, and nothing says so.

### 4.8 "Fully filled-in example" is 4 files of ~10 — MED

- **Files**: `README.md:87` ("See `examples/` for a **fully filled-in** fictional project"), `docs/getting-started.md` ("a **complete** filled-in example") vs `examples/` contents: `CLAUDE.md` + `context/{architect,backend,database}.md` only.
- Missing examples, by difficulty to write blind: `local-dev.md` (**highest impact** — it's what the verify/auto-demo machinery executes against; the Ephemeral Per-Item DB section is genuinely hard to get right blind), filled `loop.config.md`, `infra.md` (most specialist), `shared-frontend.md`, `app.md`, `admin-app.md` (the example TaskFlow project *has* an admin app — unforced omission). Also: no example `docs/features/<slug>/` folder — adopters never see a finished requirements/design/brief, only templates.

### 4.9 The example database primer violates its own conventions — LOW

- **File**: `examples/context/database.md`. Its Conventions say "Foreign keys always specify `onDelete`" — but `tasks.workspace_id`, `time_entries.user_id`, `time_entries.workspace_id` specify none. It also says "Most have `updated_at` (except time_entries)" while `database-engineer.md`'s quality bar mandates `created_at` + `updated_at` on every new table. As the model users imitate, it contradicts the rules engineers are graded against.

### 4.10 `examples/CLAUDE.md` drifted behind the template — LOW

- Template's "Agents and Modes" now includes loop modes + specialist agents; the example shows only the pre-loop lines. Users copying the example's shape drop the lines the template says to keep.

### 4.11 Hygiene: stray files ship via copy — LOW

- `.claude/.DS_Store` (6 KB Finder artifact — the kit dir isn't a git repo, so copy-based distribution ships it) and empty `.claude/worktrees/` (machine artifact; also un-gitignored should the host ever populate it).

### 4.12 Advisory: "read-only" critics are prompt-level only — LOW

- code-reviewer / design-critic / security-reviewer all have `Bash` in `tools:`, which permits arbitrary writes. Acceptable as an advisory boundary; worth a one-line acknowledgment in the agent files (as guard-git.sh already models for its own limits).

*(Verified fine, for the record: agent/command frontmatter keys and tool names are all valid; settings.json schema and hook wiring are correct; `.claude/CLAUDE.md` is genuinely loaded as project instructions; always-loaded token footprint is small (~1.6k tokens) — nothing bloated.)*

## Cluster 5 — Public-OSS packaging

Essentially absent, while the internal design rigor is exceptional — the gap between the two is the cluster.

### 5.1 No LICENSE file — HIGH ✅ verified absent

- `README.md` says "## License / MIT" but no LICENSE file exists. Without the MIT text + copyright line the grant is legally ambiguous; some orgs' policies block adoption on this alone. Cheapest HIGH fix in this document.

### 5.2 No update story — HIGH

- Install is `cp -r` — a one-way fork. When the kit ships fixes (this document guarantees it will), adopters have no way to pull them: no version marker in the copied files, no kit-files-vs-your-files manifest (the README's edit/leave-alone lists are a good basis but framed for customization, not updates), no suggested mechanism (git subtree, a sync script, release diffs). Since adopters *edit files in place*, updates will conflict invisibly.
- **Fix direction**: stamp a `KIT_VERSION` in `.claude/CLAUDE.md` or a marker file; publish a CHANGELOG; document one supported update path (even "re-copy these never-edit files, diff these sometimes-edit files").

### 5.3 No versioning or CHANGELOG — MED

- The design doc has rich internal versioning ("LOCKED v3", Revision 1/2) but the kit itself has no version, tags, or changelog. Adopters can't tell what they installed or what changed.

### 5.4 No compatibility statement — MED

- See 4.6 for the dependency inventory; the packaging-layer fix is a Prerequisites/Compatibility section in the README.

### 5.5 No CONTRIBUTING / CODE_OF_CONDUCT / issue templates — LOW

- Standard scaffolding for a public repo inviting adoption.

## Cluster 6 — Real-team coverage gaps

Things a real adopting team hits in the first weeks that the kit is silent on. All MED/LOW; none break the kit, all generate support questions.

- **6.1 Testing strategy — MED.** The kit *enforces* tests (verify gate; engineer-protocol "Tests to write") but never *advises*: framework choice, unit vs e2e expectations, what a smoke test should assert, or the brownfield-zero-tests path (4.7). CLAUDE.md's only nod is a parenthetical about relaxing test requirements — with no section to record that in.
- **6.2 CI integration — MED.** Zero mentions. Should CI re-run `verify_tests`? Do feature folders / briefs / metrics get committed? How does "never push" interact with CI-on-push teams?
- **6.3 The deployment cliff — MED.** Local-first is well-argued (§8a), but the day the "later milestone" arrives has zero guidance: SQLite→Postgres in practice (design admits "low-friction, not free"), first deploy for the beginner audience told to delete the infra agent, loop behavior across the deploy boundary. The beginner path currently ends at localhost.
- **6.4 Monorepo/multi-repo — LOW-MED.** The example is a pnpm monorepo and CLAUDE.md asks the question, but polyrepo teams (contract across a frontend repo + backend repo; where does `.claude/` live; can the loop span repos — no) get no answer.
- **6.5 Multi-developer usage — LOW-MED.** "Small teams" are in the audience, but everything assumes one human: one run lock, one local main, "you review + push." Two devs running modes simultaneously, or a teammate pushing mid-run — undiscussed. Also no personal-vs-shared-committed guidance for `.claude/` files.
- **6.6 Mid-run single-item abandon — LOW.** User-initiated abandonment of one in-flight item (vs. loop-raised `PLAN_REVISION_NEEDED`) is only implicitly `/planner`'s job; the abandoned item's status/branch are uncovered. (Cross-feature contract drift is an acknowledged §15 deferral — safe interactively, moot in the sequential loop.)
- **6.7 `verify_tests` ">0 tests collected" — LOW.** Requires parsing framework-specific output; no per-stack guidance.
