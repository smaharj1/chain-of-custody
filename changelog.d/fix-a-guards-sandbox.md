# fix-a: review fixes for the guards, the sandbox profile, the settings templates and the guard corpus (GD-1 to GD-9, IN-10, D1, D3, D10, D11)

## Changes

- `guards/g_exec.py` classifies `loopctl` with `kitlib/loopctl_table.classify` (read / write / human) instead of its own copy of the tables. The action is the next word only when it does not start with `-`, so `loopctl lock --session status steal` is a write (GD-1). The **human** class is denied to every caller, the registered conductor included (`guard-exec:loopctl-human-only`): `approve` with any scope or choice the conductor may not relay, `resume`, `reconcile --live`, `reconcile --apply --prs|--rule-suites`, `parallel ... --apply`, `migrate-plan ... --force`, `remote-lock acquire|renew|release|steal`, `claim take|release` (D11, D3). A word the guard cannot read in the command position, or anywhere in one of those commands, is a human step. A `loopctl` command line inside inline code or an agent-authored script is read out of the text and judged the same way; a symlink to the `loopctl` package is `loopctl`. `LOOPCTL_READ`, `LOOPCTL_FLAG_READ`, `LOOPCTL_WRITE_FLAGS` and `_loopctl_parse` are gone; `loopctl_classify(inv)` is new and `loopctl_is_read(inv)` stays as a thin wrapper (the HALT guard uses it).
- `guards/g_git.py`: `git push` is denied to every caller. The conductor's delivery push (`push-branch`, `draft-pr`, `pr-automerge`) is gone; whatever the old conductor checks let through is now `guard-git:push` (GD-4, D3).
- `guards/g_exec.py` `kit-internals` now applies to agent-authored **script files** (GD-2, D1 item 6): the writers of run state (`register_session`, `set_halt`, `acquire_lock`, `write_nonce`, `write_run`, `sessions_dir`, `loopctl/sessions|run.json|HALT|lock|nonces` however the path is split), the local Python modules such a script imports (transitively, at most 10 files of 256 KB), and code that imports `loopctl` and calls `main`, `Loop`, `approve`, ... (D11 item 7). Inline code keeps the full `KIT_INTERNALS_RE`.
- `guards/paths.py`: `agent_authored` counts a tracked, clean file as reviewed only when it is also unchanged from every trusted base: the active run's `baseSha` and the merge-base of `HEAD` with `origin/HEAD`, `main` or `master` (GD-6). No base: agent-authored.
- `guards/g_exec.py` `human-apply` covers the bootstrap apply paths (GD-8, the Phase 9 audit that 11a deferred): `bootstrap_config.py apply`, `github/labels.py --apply`, `github/boundary.py --apply|--run`, `apply-boundary.sh`, `apply-labels.sh` (`--apply`), `verify-boundary.sh --run`, a generated `.claude/bootstrap/setup.sh --apply`, besides `migrate.py` and `init_project.py`. Matched by basename, by the real path of a symlink, as `python -m`, and with an unambiguous abbreviation of the flag (`--ap`). Generic names (`labels.py`, `setup.sh`, `boundary.py`) need the kit's directory in the real path, so a project's own `setup.sh` is not caught.
- `guards/g_infra.py` (IN-10): a tool is a read only when its first word is a read verb and no later word is a mutating one (`check_and_apply`, `get_or_create_*` are not reads; `list_open_issues` still is). A tool that runs a command line it is handed (`call_aws`, shell, cli, eval, terminal) is **asked** in a main session.
- Sandbox (GD-3, D1): `guards.paths.SANDBOX_DENY_WRITE` is the one list (the whole H6 write set plus `.git/loopctl/sessions`, 33 entries). `templates/security/sandbox.settings.json` carries it as `denyWrite` and as `Edit(...)` denies; the generated `templates/settings/*` carry the same sandbox block; `wiring.DENY_BASELINE` repeats the Edit rules. `wiring.py --sandbox-snippet` prints the absolute git-dir lines for a linked worktree and writes nothing. `templates/security/mcp-lockdown.settings.json` and the shared deny block carry the infra MCP deploy-deny list (`wiring.MCP_DEPLOY_DENY`, equal to `templates/infra/mcp-deploy-deny.settings.json`).
- Doctor: `sandbox.deny-paths` wants the whole write set (ERROR when a write entry is missing, WARN for a missing credential directory as before; a denied parent directory counts for its children); new `sandbox.registry-path` (the registry must be denied; in a linked worktree by absolute path; ERROR with `runner: driver`, level L2 or higher or unattended, WARN otherwise); new `guards.v1-residue` (D10).
- GD-8: `guards/cli.py` state commands, `github/boundary.py`, `apply-boundary.sh` and `verify-boundary.sh` use `humanonly.refusal` / the either-marker-even-empty test.
- `docs/security/guards.md`: the three loopctl classes with the human-only table generated from `loopctl_table` (compared by `tests/guards/test_guards_doc.py`), no agent push, scripts the agent wrote, the v1 hooks and their removal, ConfigChange scope (GD-9). `docs/security/sandbox.md`: what the profile covers and does not, the registry, linked worktrees.

## Decisions made

- **Conductor push denies keep their specific rule ids.** D3 allows either. The old conductor branch (`push-tainted`, `push-delivery`, `push-protected`, `push-force`, `push-refspec`, ...) stays as the more specific message, and the former allow path now ends in `guard-git:push`. Only the four allow rows flipped; the other conductor deny rows and the synthetic eval transcripts keep their rule ids. The deny is unconditional, so nothing weaker than D3 results.
- **Reviewed-script base is the union.** D1 says `baseSha` when a run is active, else the merge-base. `run.json` is writable from the sandbox on purpose, so a forged `baseSha` at HEAD would launder a conductor-committed engineer script. A file is reviewed only when unchanged from every available base (`baseSha` and the merge-base). Stricter than D1, never weaker.
- `SANDBOX_DENY_WRITE` is wider than D1's list where the H6 table is wider: `.github` as a whole (D1 named `.github/workflows` and `CODEOWNERS`), `.gitlab-ci.yml`, `.gitlab`, `.circleci`, `Jenkinsfile`, `azure-pipelines.yml`, `.buildkite`, `bitbucket-pipelines.yml`, `.travis.yml`, `docs/CODEOWNERS`, `.claude/workflows`, `.claude/managed-settings.json`, `.mcp.*.json`, and the glob `.claude/settings*.json` next to the three named settings files. The test requires every H6 pattern to be covered.
- `wiring.DENY_BASELINE` now also carries the Edit rules for the whole list and the MCP deploy-deny patterns, so the headless-child, critic and interactive profiles are in step with the sandbox template. This makes `guards.deny-drift` report more missing entries for installs that merged the old baseline (a warning, as before).
- Dynamic words: a `$x` or `$(...)` in the `loopctl` command position, or anywhere in `approve`, `reconcile`, `parallel`, `migrate-plan`, `remote-lock`, `claim`, `resume`, makes the call a human step (fail closed). `loopctl status "$id"` is unaffected.
- `verify-boundary.sh --run` and `boundary.py --run` are treated as human apply steps (they use the human's `gh` login), although they only read.
- `sandbox.deny-paths` severity: ERROR when a write entry is missing (it is the H6 gate), WARN for a missing credential directory (unchanged).
- A tool name containing `call`, `cli`, `shell`, `bash`, `terminal` or `eval` is asked in a main session (IN-10 "call_aws / generic exec"). Names such as `call_tool` are asked too: a prompt, not a block.
- GD-8 list from `grep -rn CLAUDECODE .claude/scripts`: fixed in `guards/cli.py`, `github/boundary.py`, `apply-boundary.sh`, `verify-boundary.sh`. Already correct: `labels.py`, `bootstrap_config.py`, `migrate.py`, `init_project.py`, `apply-labels.sh`, the generated `setup.sh`. **Known gaps**

- The guards are a typo guard against code: a script that builds the registry path from computed arithmetic, a module found through `sys.path`, or a Node `require` chain is not seen. The sandbox `denyWrite` on `<git-common-dir>/loopctl/sessions` is the real stop and is only as good as the platform's enforcement (probe, V19). `run.json`, `lock`, `HALT` and `nonces/` stay writable from the sandbox on purpose.
- `--by` on `loopctl approve` is recorded, not authenticated; a human who pastes a conductor-printed command without reading it is outside the kit's reach. `loopctl approve` has no `CLAUDECODE` check on purpose (relay by `!`); the guard is the only enforcement, and `!` is not seen by it.
- A `loopctl` command assembled from pieces inside code (`'loop' + 'ctl'`) is not read. The guard reads the text, it does not run it.
- The tripwire in the human scripts (`humanonly`) passes `env -u CLAUDECODE -u CLAUDE_CODE_ENTRYPOINT`; the `human-apply` rule is what denies the agent that does that, and only for the names in its table. A copy of `labels.py` under another name outside a `github/` directory is not recognised.
- A kit-development session that runs untracked tests importing `loopctl` and calling into it would trip `kit-internals`; kit development runs without these guards until the release.
- Until the release stage the live `.claude/settings.json` still wires the weak v1 hooks (not edited here: hot file).
- The generated `plugin/`, `dist/copy-install/` and `.claude/KIT_MANIFEST` are stale until the conductor rebuilds them; the drift test in `tests/dist/` fails in this worktree for that reason only.
