# 11a-bootstrap-ops: /bootstrap, the receipt, human-run GitHub setup, intake / dependency / smoke workflows

## Changes
- **`/bootstrap`** (`.claude/commands/bootstrap.md`): a human-only mode that takes a new or existing repository to a working kit install. Steps: detect (read-only), interview, stack into `.claude/CLAUDE.md` and the primers, a **config plan**, a **human-run setup script**, doctor and workflow lint, receipt. It runs no `gh`, no git write, and does not edit `loop.config.md`, `.github/**`, skills or scripts (the guards deny those; the flow never needs them). Refuses in a child session.
- **`.claude/scripts/bootstrap_detect.py`**: read-only facts (`bootstrap_detect.v1`): greenfield/existing hint, stack from manifests, suggested verify commands (from fixed tables: a `package.json` script name is looked up, its body is never read), deploy-host files, installed ops workflows, kit/CLAUDE.md/loop.config state, receipt state, **release automation** (release-please, changesets, semantic-release, goreleaser) with evidence and suggested `always_human_paths`. Git runs with config isolated, hooks pinned off and `core.fsmonitor` forced off; remote URLs are reduced to host and OWNER/NAME (tokens never printed).
- **`.claude/scripts/bootstrap_receipt.py`** and `.claude/bootstrap-receipt.json`: `init`, `run`, `record`, `emit`, `finish`, `check`, `show`, `status`. Per step: command, exit code, SHA-256 of output, `source: ran|recorded`. Entries are hash-chained. `run` executes only the kit's read-only scripts (doctor, ci_lint, bootstrap_detect, probe_run without `--go`, `guards/wiring.py --check`, loopctl `doctor|validate|status`) by exact path and flag allowlist, no shell, scrubbed environment, timeout. Atomic writes under an exclusive lock. A hostile or damaged existing receipt is never appended to.
- **`.claude/scripts/bootstrap_config.py`**: `plan` validates `KEY=VALUE` against the registry (known key, type, choices, evidence gate, no `<command>` placeholder) and writes `.claude/bootstrap/config-plan.json`; `apply` (human-only, dry run unless `--write`) re-validates, edits only the planned value tokens in `loop.config.md`, parses the result and refuses unless exactly the planned keys changed.
- **`.claude/scripts/github/repo_script.py`**: prints the GitHub-side setup as a POSIX shell script (`.claude/bootstrap/setup.sh`, phases `local` and `remote`, dry run unless `--apply`, refuses in a session). Steps: `gh repo create` + first push (greenfield), `apply-boundary.sh`, `apply-labels.sh`, `FACTORY_APPROVERS`, workflow copies (never over an existing file), the config plan, the `launch-app` skill. The generator has no way to start a program.
- **Labels:** `.claude/templates/github/labels.json` (factory:feature/bug/deps/chore/go/requested/running/halt, plan-ok, preview) and `.claude/scripts/github/{labels.py,apply-labels.sh}` (one `gh label create --force` per label; dry run by default; prints every call; refuses in a session). `.claude/scripts/humanonly.py` holds the shared refusal check (`CLAUDECODE` and `CLAUDE_CODE_ENTRYPOINT`).
- **Workflow templates** (`.claude/templates/github/workflows/`), all clean under `ci_lint.py` apart from the SHA-pin warning: `intake.yml` (approver's `factory:go` -> tool-less triage job with no write token -> `intake_validate.py` and a write job with no model), `dependency-check.yml` (scan job read-only, report job writes issues), `smoke.yml` (project code in a read-only job; a second job opens one `factory:bug` issue). Helpers: `.claude/scripts/intake_validate.py`, `.claude/scripts/dependency_report.py` (majors, osv advisories, lockfile peer mismatches, primer-vs-lockfile drift).
- **Docs:** `docs/bootstrap.md`, `docs/ops.md`, `docs/release-automation.md` (H5), including the F-25 prose ("More than one human") and the design-only parts. `.claude/templates/launch-app-skill.md` (the "project `/run` skill" step of Q6, named `launch-app` so it never collides with bundled `/run`).
- Fixes in code this phase touched or found: `boundary.py` slug regex now ends in `\Z` (a trailing newline passed); `tests/test_frontmatter.py` accepts the later modes (`bootstrap`, `retro`) beside the core five.
- New tests: `tests/bootstrap/` (10 modules, 183 tests; the slowest module takes about 4 s; the whole suite stays near 30 s).

## Upgrade impact
None for a v1.2.0 install that does not use these files: no existing file changes behaviour, no config key is added, no hook is wired. A new `/bootstrap` command appears. Projects that want the ops workflows copy them (the setup script does) and pin the actions.

## New config keys
None. Bootstrap writes existing keys only (`github_repo`, `solo_maintainer`, `factory_approvers`, `verify_*`, `delivery`, `always_human_paths`, `deploy_triggers` is attested by the human). `factory_approvers` is Phase 1's and is not redeclared.

- **Text for `docs/design/deferred.md` (release stage; DESIGN-ONLY, IMP-25):**

  ### UAT feedback widget
  What: a "report a problem" control inside the app for testers, so the report arrives as an issue with the environment and build attached. Design: the control posts to an endpoint on the app's own server (never GitHub from the browser). The endpoint holds a fine-grained token limited to Issues: write on one repository, rate-limits per session, and files an issue labelled `factory:requested` (never `factory:go`). Fixed fields come from the build and request, not the tester: commit sha stamped at build, environment name, route, user agent, timestamp. The tester's words go in a fenced block marked untrusted; screenshots are stored by the app and linked, not uploaded to GitHub. The text is untrusted (report 5.3): it reaches the loop only through two-stage intake after an approver applies `factory:go`. Why design-only: it is application code (framework, auth, hosting differ per project) and needs a live token and a real UI to test; the kit ships no UI. Unblocked by: a project with a chosen stack and a scoped token; then an offline contract test of the payload-to-issue mapping.

  ### Monitoring to intake (F-14)
  What: an uptime or error monitor files or updates a bug issue without a human copying it. Design: the vendor's GitHub integration or a small webhook function, using the same narrow token, opens one issue per signal (stable title, deduped by a fingerprint in the title), label `factory:bug`, body of fixed vendor fields plus a link; any log or stack trace is fenced and marked untrusted; severity is mapped from the vendor's scale onto the closed set; a flood limit at the receiver. Never `factory:go`. `smoke.yml` is the in-repository version of the same loop. Why design-only: vendor-specific and needs a live monitor and token. Unblocked by: a chosen vendor.

  ### Reproduce-first bug lane (Q4)
  Flow: `factory:bug` issue -> two-stage intake (built) -> triage: severity, duplicates, repro steps -> a failing test committed first as the acceptance criterion (G3 acceptance-author) -> fix through the quick lane -> verify -> pull request. Severity high or critical, or a change under `always_human_paths`, is never auto-merged. Built: labels, `intake.yml`, the schema fields `severity`/`repro_steps`/`duplicate_of`, the smoke issue. Design only: the loop-side consumption (turning a triaged issue into a plan item and running the lane). Unblocked by: loopctl's intake (Phase 7) and G3.

## Decisions made
- **Config goes through plan and apply, not through the agent.** Nearly every registry key is H6 (only `db_local`, `git_strategy` and `model_profile` are not), and the file guard denies an agent edit that changes an H6 key. So `bootstrap_config.py plan` is agent-safe and `apply` is human-only with a diff and a parse-back check. It edits value tokens in place so the generated comments and alignment survive.
- **The setup script has two phases** (`local`, `remote`) because a ruleset must follow the first push and a config or workflow edit must be committed before it. Kit scripts inside it get `--apply`/`--write` only when the human passes `--apply`.
- **The receipt is a record, not a gate.** Chained entries catch accidents; `finish` needs `detect` and `doctor` and no step whose last attempt failed. A doctor exit of 1 ("errors present") is an answer, so it counts as ok for that script; `ALLOWED` in `bootstrap_receipt.py` carries each script's ok exit codes. `run` deliberately cannot run `verify.py` or any project command (primer-protocol: unknown repos' commands run only in the probe sandbox).
- **loopctl is named, not imported.** The `run` allowlist accepts `.claude/scripts/loopctl` with `doctor`, `validate`, `status` only; if Phase 4a names them differently, edit `ALLOWED`.
- **Intake triggers on an approver's `factory:go`, not on issue creation**, so a stranger cannot spend the API key. The workflow re-checks the approver itself because `label-guard.yml` runs concurrently. There is no tool-bearing LLM stage: stage 2 is a deterministic script. The type labels are approver-only like the other `factory:*` labels (the workflow's own `GITHUB_TOKEN` events do not trigger label-guard).
- **The intake schema is embedded** in `intake_validate.py` (fields: type, title, problem, acceptance, severity, repro_steps, duplicate_of) because Phase 7's `intake_schema.json` is not merged yet. Reconcile at merge.
- **`humanonly.py` checks two markers** (`CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`) so `env -u CLAUDECODE` alone is not enough; presence counts, not value. It remains a tripwire (documented gap, same as `apply-boundary.sh`).
- **Labels: `plan-ok` and `preview` are in the list** because `label-guard.yml` protects them and the infra templates use them.
- **`launch-app`, not `run`,** is the generated project skill's name (bundled `/run` looks for a project skill that already launches the app; `run`, `loop` and `code-review` are reserved). A human installs it because a skill's frontmatter can run hooks (RC-18).
- **Release tools:** semantic-release and goreleaser are detected beside release-please and changesets, matching what the Phase 1 doctor already treats as release automation.
- **Primer drift is a heuristic** (`name@N`, `name vN`, `name N.x` for names that are real lockfile dependencies; `package-lock.json` and `poetry.lock` only). It opens issues, never edits a primer.
- **`mode_hint`** is `existing` only with a commit and some code or manifest; a README-only repo is greenfield. The human confirms.
- Edited two files owned by earlier phases, minimally: `boundary.py` (`\Z`), `tests/test_frontmatter.py` (accepts `bootstrap` and `retro`). Appended to `tools/check-refs.allow` and `.gitignore` (`.claude/bootstrap/`).
- Adversarial findings fixed in this phase: option-like repo names (`-rf/x`) passed the slug pattern; `$` matched before a trailing newline in four slug/colour regexes; `core.fsmonitor` in a repository's own config ran on `git ls-files`; `cp -n` exits 1 on BSD when the target exists; a nested-JSON file raised RecursionError in six loaders; primer drift compiled one regex per dependency; `show_plan` crashed on a multi-line config value. Each has a test row in `tests/bootstrap/`.
