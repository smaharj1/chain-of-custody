# 11b-loopctl-extras: remote ref lock, multi-human claims, reproducibility manifest, G10 product checks, L5 eligibility classifier (nothing merges)

## Changes

- **Remote lock** (`.claude/scripts/loopctl/remote_lock.py`, OPT-IN, evidence-gated): `refs/loopctl/lock/<plan>` on the remote named by `remote_lock`, a commit whose tree is one `lock.json` with the lease record shape of `parallel/mutex.py`. Create-only (`--force-with-lease=<ref>:`), heartbeat and takeover by compare-and-swap, release by lease-guarded delete. Stale = heartbeat past the record's ttl (`lock_stale_min`) **and** the owner gone (a dead pid on this host; another host only with `--host-dead`). A ref that is not exactly a valid record (blob, second file, non-strict JSON, other plan, unknown field, future heartbeat, absurd ttl) is `corrupt` and counts as held; `steal --corrupt` replaces it. `Keeper` holds it inside a driver run (token file under `<git-common-dir>/loopctl/remote-lock.json`, mode 0600) and is the driver's stop hook: a lost lock stops the run, an unreachable remote stops it after half the ttl. A push the remote refuses (a ruleset, a hook) is reported as a refusal, not as a lost race. Advisory, not a boundary (RC-12). Spec: `.claude/spec/loopctl-extras.md`.
- **Claims** (`loopctl/claims.py`, F-25): `refs/loopctl/claim/<plan>/<item>`, same shape. First push wins; the same name renews; `claim_ttl_h` later anyone may take over (the record names the old holder); `--override` replaces a live claim and is recorded as one; an unreadable claim ref counts as claimed. The driver never takes a claim and skips items others hold (`remote_lock.ClaimsFilter`; falls back to "nothing eligible", never "everything"); when only claimed items are left it stops with outcome `claimed` (`unattended` reports it as "waiting").
- **Commands** (`loopctl/extras.py`, wired in `cli.py`, classified in `cli.py` and `guards/g_exec.py`, 55 new rows in `tests/guards/corpus/loopctl.json`): `remote-lock status|acquire|renew|release|steal`, `claim list|show|take|release`, `merge-class ITEM`, `manifest write|show|verify`. Reads: `merge-class`, `remote-lock status`, `claim list|show`, `manifest show|verify`. Writes (Tier 1, conductor session only): the rest.
- **Run wiring**: `startrun.preflight` prints `remote-lock` and `claims` rows when `remote_lock` is set (a run that cannot take the lock does not start); `startrun.start` takes the lock after the local one for `runner: driver` and gives it back before; `Driver` gains `item_filters`, `held_back`, `eligible_now` (the serial driver and the parallel scheduler both use it) and attaches the keeper only when one exists. A run without `remote_lock` loads none of this.
- **L5 classifier** (`loopctl/merge_class.py`): `classify(facts)` is pure and answers "would this item be eligible for a low-risk lane if auto-merge existed"; `action` is always `human-merge` and `merges` is always false. Eleven rules (policy, level, evidence, promotion, mutation, deploy, paths, item, gates, ci_fix, flag), every missing fact a failure. **B5**: judged from the attestation (`deploy_triggers`, `git_integrated_hosts`, `deploy_surface.*`); an unattested surface, an ungated or malformed trigger or host, a misspelled gate, all fail. A repo that deploys on merge to main without a human gate is never eligible. **Paths**: case-folded, `..`/absolute/backslash/NUL/`.git` refused, symlinks and submodules never low-risk, renames judged as delete plus add, H3 list + deploy-surface floor + `always_human_paths` + security-sensitive words in non-document paths. No code path merges: `merge_policy` is a closed enum, default `human`, H6, evidence-gated for `auto-low-risk`.
- **Doctor** (`doctorlib/extras.py`, imported by `doctor.py`; `levelcalc.py` asks it): `l5.merge-policy` (an error for `auto-low-risk` until evidence, promotion bar, G4 `on` and B5 hold) and `l5.b5`; `lock.remote`; `g10.config`; **`fork.env`** (a): builds the engineer and critic profiles the driver would launch and asserts `CLAUDE_CODE_FORK_SUBAGENT=0` and `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, checks any `--settings` file given, and for the prose conductor reports advice only. Every message says `[probe V18]`: the names are the report's assumption and the loop does not depend on them. **(b)** `levelcalc` adds `notify_command usable` and `external watchdog has checked in` to the L4 prerequisites and `merge_policy is auto-low-risk` and `low_risk_paths` to the L5 ones. The two L4 rows are `loopctl.unattended.notify_row` and `watch_row`, which `unattended.rows` now also uses, so `loopctl unattended check`, `loopctl run` and the doctor print the same judgement.
- **Manifest** (`loopctl/manifest.py`, F-26): sealed JSON of base/head, KIT_VERSION, the config hash and gate modes at the base, plan and item digests, toolchain pins, lockfile object ids, verify commands, the evidence blob, recorded gate results and environment. `verify` checks the seal and re-derives everything git can re-derive at the recorded commits, so edit-and-reseal fails; `--expect-hash` covers the recorded-only fields; the event log reports whether this machine wrote the hash. Not a signature.
- **G10** (`loopctl/gates/g10_product.py`, OPT-IN, evidence-gated, no tooling bundled): four named checks (`g10_a11y_cmd`, `g10_perf_cmd`, `g10_pii_cmd`, `g10_observability_cmd`), each run **without a shell** (shell syntax refused like `notify_command`), refused if the program or an argument is a file the item changed, given `LOOPCTL_G10_SCOPE`, and judged on a `g10.v1` result line (`checked >= 1`, `violations == 0`, extra fields and wrong check names are failures). `gates/_ci.py` gains `g10`; `.claude/templates/github/workflows/g10-product.yml` is the CI half; `driver.VERIFY_GATES` gains `g10` (a no-op while `off`). **Contract tests against `api-contract.md` are DESIGN-ONLY**: written up in the spec, no key, no code, no test (the test only asserts that).
- Docs: `docs/loopctl-extras.md` (operator guide), `.claude/spec/loopctl-extras.md` (spec).
- Tests: `tests/loopctl/extras/` (6 modules, 84 tests) and `tests/doctor/test_extras.py` (13), 97 in all. About 7.5 CPU-seconds in all, none over 2.2 s alone; the lock and claim rules run over an in-memory compare-and-swap remote, and the git behaviour (create-only leases, a ref that is not a lock, a remote that refuses, two real clones racing) runs against a local bare remote built once per class. `tests/doctor/test_level_caps.py` (the `Ready` fixture), `tests/loopctl/test_gates.py`, `tests/loopctl/gates/test_evidence.py`, `tests/loopctl/fault_injection/test_flow_happy.py` and `tests/loopctl/test_guard_alignment.py` changed to match (see "Decisions made").

## Upgrade impact

None for anyone who does not opt in. `remote_lock` is empty, `merge_policy` is `human`, `gates.g10` is `off`; a run without `remote_lock` loads none of the new modules. A v1.2.0-to-v2 install gains ten registered keys (below), four `loopctl` commands, the `l5.*`, `lock.remote`, `g10.config` and `fork.env` doctor rows, and the two L4 prerequisites. **The L4 and L5 rows can lower an existing configuration's effective level**: an install that configured L4 now also needs a usable `notify_command` and a watchdog that has checked in (Phase 7 already required both to start an unattended run), and one that configured L5 needs `merge_policy: auto-low-risk`. Nothing reached L4 before the evidence gate could pass, so no real install is affected.

## New config keys

All owner `11b-loopctl-extras`, section "Loopctl extras" (`gates.g10` sits in `kitlib/schema/4b-gates.json` next to `gates.g4`, because the registry requires the `gates.*` keys to be contiguous).

- `merge_policy` (enum `human|auto-low-risk`, `human`, H6, evidence-gated for `auto-low-risk`).
- `low_risk_paths` (list, `[docs/**, "**/*.md"]`, H6): globs an item may touch and still be low-risk; never widens the never-list.
- `remote_lock` (string, empty, H6, evidence-gated for any value): a git remote name.
- `claim_ttl_h` (int, 72, not H6).
- `gates.g10` (enum `on|report|off`, `off`, H6, evidence-gated for `on` and `report`).
- `g10_a11y_cmd`, `g10_perf_cmd`, `g10_pii_cmd`, `g10_observability_cmd` (command, empty, H6): no shell, see above.
- `g10_timeout_s` (int, 600, H6).

## Pending-human actions

- **Run the remote lock against a real remote** once, from two machines (or two clones), on a throwaway repository you own: `remote_lock: origin` in a committed config, `loopctl remote-lock acquire` on one and `acquire` then `steal --host-dead` on the other. Confirm the host accepts the create-only push (`git push --force-with-lease=refs/loopctl/lock/<plan>: ...`), refuses the second, and that `refs/loopctl/*` is not blocked by a ruleset. Needs a real remote and two machines; agents may not push (IMP-14) and the tests use local bare repositories only.
- **Run G10 with one real tool** (axe, Lighthouse CI or your own script) on a real app and commit what the wrapper prints as `g10.v1`; pin the actions in `g10-product.yml` to commit SHAs. Needs a real app, browser and toolchain.
- **V18 probe** (`tools/probes/`, probe-assumptions V18): confirm `CLAUDE_CODE_FORK_SUBAGENT` and `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` exist and do what the report says; if the names differ, change `launch.FORK_ENV` and `doctorlib/extras.py` `FORK_ENV_EXPECTED` together. Needs the real `claude`.
- **L5 stays off.** Enabling is design-only by policy (IMP-1). Nothing to do unless you decide to build it; if you do, it needs the evidence gate, a promotion bar from server-side facts (`loopctl unattended promotion`), mutation testing on, and a repo that does not deploy on merge to main.
- **Schedule the external watchdog** (Phase 7's `loopctl unattended watch`, cron or launchd): the doctor now needs it for L4, not only the start of an unattended run.
- Commit `remote_lock`, `merge_policy` and `gates.g10` only through review (H6), after the evidence gate passes.

## Decisions made

- **`gates.g10` lives in `4b-gates.json`.** The registry rejects `gates.*` keys that are not contiguous in registry order, and 4b's `gates.g4` is the only specific one. The entry is owned by `11b-loopctl-extras` (`owner_phase`), the file edit is 22 inserted lines.
- **`merge_policy` is an enum of two values, `human` and `auto-low-risk`.** The report's DEC-3 names the opt-in and the default but no values; two closed values cannot be smuggled into a third meaning (the tests try `auto`, `auto-merge`, `pr-automerge`, `true`, a value with `gh pr merge` in it). It is evidence-gated, H6 and read from the base sha. `delivery: pr-automerge` stays unregistered (Phase 3).
- **L5 needs the policy switch.** `levelcalc` adds `merge_policy is auto-low-risk` to the L5 prerequisites, so "configured L5, policy human" is effective L4 with the reason printed. The `Ready` fixture in `tests/doctor/test_level_caps.py` now sets it (and `notify_command`, and a watchdog check-in for L4).
- **The classifier is the second wall for B5, not the first.** It judges the attestation in loop.config (it cannot read workflows); the doctor's `b5-deploy-surface` cap reads the workflows and the effective level must be L5. The classifier needs both.
- **`merge-class` takes the level from the doctor and treats "unknown" as "not L5".** Against the test double (`KIT_CLAUDE_BIN` a fake) it would get `None`; tests set `extras.LEVEL_FN`.
- **A document is `.md .rst .adoc` or a plain image; everything else under `low_risk_paths` is "copy".** An svg can carry a script, so it is copy and needs a feature flag. The security-sensitive word list is applied to non-documents only (a document that talks about auth is still text), and the deploy-surface floor is matched over-approximately (a docs file named `Dockerfile.md` is refused; that is the safe direction).
- **G10 commands run without a shell and are refused if the item changed them.** The other command keys (`mutation_cmd`, `verify_*`) are shell strings; G10 follows `notify_command` instead because a G10 check is a judge, and a judge whose command line can say `; curl ... | sh` is a hole. Cost: wrap pipes in a script. Gap: a check that imports another repository file is only protected for the files named on its command line; keep the check outside the item's reach (the doc says so).
- **Scope of G10**: changed files minus tests, documents (`.md .rst .adoc .txt`), `docs/` and `plan/`; nothing left means `skipped`. "Routes" are the command's business.
- **Claims use the lock's mechanism, one ref per item, and the lock owner's name is the claim name.** A driver run counts as `LOOPCTL_USER` or the OS user, so a person who claimed under another name blocks their own run until they claim under that one (documented).
- **The remote lock is taken for `runner: driver` only.** The prose conductor has no heartbeat to keep it fresh; it uses `remote-lock acquire|renew|release` by hand (documented) and the preflight row still keeps a second machine from starting a driver run.
- **Reading a lock is fetch plus one batched `cat-file`** (two processes), into `refs/loopctl/cache/...`; the batch reads a forged object whole. Acceptable for an advisory lock: someone who can write the ref could just delete it.
- **No fast-import, no ls-remote in the hot path.** Measured: `git fast-import` saved 5 ms a write and added a mechanism; the three-step commit is the state ref's plumbing.
- **The manifest records a `hash` but is not committed anywhere.** Where the hash is published (the PR's audit block) is the conductor's choice; `audit.py` is 4a's file, so a `Manifest:` line there is a pointer.
- **`manifest verify` re-derives from the recorded shas, not the current branch**; a manifest from another repository fails with "does not have commit".
- **`driver.VERIFY_GATES` gains `g10`** (the Phase 10 note allowed it): a no-op while `off`; the stub-gate flow test lists it.
- **`unattended._WAITING` gains `claimed`** so an unattended run that stopped only because of other people's claims reports "waiting for you", not "stopped".
- **Test budget**: the in-memory remote double (`tests/loopctl/extras/__init__.py`, `MemRemote`) tests the rules; the real bare remote tests what git does. Without it the two modules cost 4 CPU-seconds.
- **Out-of-scope edits and why**: `kitlib/schema/4b-gates.json` (contiguity, above); `loopctl/gates/_ci.py` (the `g10` subcommand); `loopctl/driver.py`, `loopctl/parallel/scheduler.py`, `loopctl/startrun.py`, `loopctl/unattended.py` (the seams above and the two shared rows); `loopctl/cli.py`, `guards/g_exec.py`, `tests/guards/corpus/loopctl.json`, `tests/loopctl/test_guard_alignment.py` (classification); `doctor.py` (one import) and `doctorlib/levelcalc.py` (the L4 and L5 rows); the generated `.claude/loop.config.md` and `examples/loop.config.md`; `tests/doctor/test_level_caps.py`, `tests/loopctl/test_gates.py`, `tests/loopctl/gates/test_evidence.py` and `tests/loopctl/fault_injection/test_flow_happy.py` (fixtures and gate lists that name `g10` or the L4/L5 rows).
