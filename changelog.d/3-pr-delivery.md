# 3-pr-delivery: interactive PR delivery (verify.py, pr_prepare.py, audit block, split-CI workflows)

## Changes

- `.claude/scripts/verify.py`: the kit-owned G6 definition, standalone and importable (`load_definition`, `run_verify`, `verify`, `parse_test_counts`, `exit_code`). Stages `build`, `lint`, `typecheck`, `item-tests`, `tests`, `smoke`. The definition is read from the **base sha**: commands and ports from `.claude/loop.config.md` at the merge-base, per-item commands from an items file (the shape of `examples/hello-loop/verify.json`), also read at the base. A required stage with no command is a definition error (exit 2), never a silent pass. Every stage runs under an allowlisted environment (no token or cloud variable of the caller reaches test code; `--env NAME=VALUE` passes one explicitly, credential-shaped names refused) in its own session; the whole process group is killed on success, failure, timeout and SIGTERM/SIGINT of verify itself. Leaks (a process outliving its stage, a verify port still bound after the smoke stage) are killed and reported. Dedicated `verify_ports` are checked free before the smoke stage (busy = `env` failure, never retried). Smoke is either a harness (`verify_run`, the v1 pattern) or a native dev server (`verify_dev`: boot, poll with a deadline, request the demo route, kill the group; loopback only). Test counts are read from unittest, pytest, jest, vitest, mocha, cargo and `go test -v` summaries ("exit 0 and collected 0" fails; an unreadable count warns). Logs go redacted to `<git-common-dir>/loopctl/verify/<item>-a<attempt>.log` (mode 0600). Flags a branch that edits the gate (`verify.kit-modified`, `verify.config-drift`). JSON schema `verify.v1`, documented in the module docstring and `docs/delivery.md`. Exit 0 pass / 1 a stage failed / 2 definition or internal error; `--apply-gate` honours `gates.g6`.
- `.claude/scripts/pr_prepare.py`: validates a feature branch and prints the commands for a **human** (IMP-25). Subcommands `init` (fills the PR body from git, the engineer reports and the saved verify result), `check`, `prepare` (check, then print), `reverts`. Read-only git only, enforced by an allowlist in the code and proved by tests that log every process started; never runs `gh`; never prints a force push. For `delivery: draft-pr` it prints `git push --set-upstream origin <branch>` and `gh pr create --draft --base ... --head ... --title ... --body-file ...` (or a plain `git push` plus `gh pr edit N` when the branch is already pushed); `push-branch` prints the push; `local` prints `git switch`/`git merge --no-ff`. Checks: no `<fill: ...>` left, no empty audit field, valid values, Verify is PASS, engineers APPROVED with a passing code review, every acceptance criterion has evidence and PASS, Doc/Primer Delta (NONE needs a `checked:` line, and a report's delta cannot be dropped), stale head sha, clean tree (untracked files under `docs/features/<slug>/` tolerated), saved verify result is a complete trusted pass for this exact HEAD, human-gated paths (H3) listed and "NONE" refused over a diff that touches one (deleted and moved files count), CI-fix commits within `max_ci_fix_attempts` and not touching workflows/tests/lockfiles, diverged remote branch, protected/malformed branch names, approver-only labels, secret-shaped text, GitHub's body limit. The body is parsed so that what is checked is what GitHub shows: hidden HTML comments, tables in code fences, indented/quoted tables, duplicate fields and a second audit block are refused. Config (delivery, caps, project human paths) is read at the base sha. Git calls pin `core.fsmonitor=false`, no hooks, no external diff or textconv. Reverts: `find_reverts` (git log, "This reverts commit") and `reverts_from_prs` (recorded `gh pr list` JSON). JSON schema `pr_prepare.v1`; `validate_body`, `parse_body`, `parse_report`, `classify_paths` are importable for loopctl.
- `.claude/templates/pr-body.md`: the PR audit-block template (named fields, engineers table, acceptance matrix, Doc Delta, Primer Delta, notes). A test keeps its field list identical to `pr_prepare.FIELDS`.
- `.claude/templates/github/workflows/verify.yml` (untrusted `pull_request` job: `contents: read`, no secrets, no OIDC; takes `verify.py` from the base sha with `git archive`, runs it with `--base <base sha> --apply-gate`, writes a step summary) and `claude-review.yml` (trusted: `issue_comment` `/review` from OWNER/MEMBER only, checks out the default branch only, fetches the PR as data with `gh pr diff`, installs the CLI at `vars.CLAUDE_CODE_VERSION` in a step with no secrets, runs `claude -p` with `--setting-sources user --permission-mode dontAsk` and read-only tools in the one step that holds `ANTHROPIC_API_KEY`, posts the result as a comment). Both pass `ci_lint.py` with no errors; the only warning is the floating `@v4` tag, which the human pins. `tests/test_delivery_templates.py` proves that, and that `ci_lint` still rejects the mistakes a human could make while adapting them (OIDC or a secret in verify, a deploy command, the review job on `pull_request`, a head checkout, no author check, a comment interpolated into a script).
- `.claude/context/delivery.md` (new): the interactive delivery flow for the Tech Lead: the two dials, what never changes, branch, WIP commit per engineer (stage by path, never `git add -A`, trailers), verify and its failure classes, the PR body, `prepare`, CI-fix rules and the `CI-Fix-Of` trailer, merge, reverts, stacked slices.
- `.claude/commands/tech-lead.md`: reads `delivery.md`; A.5/B.3 branch check honours `git_autonomy` (the conductor creates `feat/<slug>` or `quick/<name>` itself at `branch` and `branch+commit`); A.6 makes the WIP commit before review at `branch+commit`; A.7 passes the commit range to the code-reviewer; A.8 step 7 becomes "Deliver" (primer commit, verify, security review, `pr_prepare.py init`/`prepare`, show the commands, stop) plus a CI-fix step 8; Lane B delivers the same way; the autonomous section says delivery is the Orchestrator's. Still: no push, no PR, no merge by an agent, ever.
- `.claude/commands/architect.md`: slices are marked human-gated when they touch an always-human path; slices are the delivery units (one PR by default, stacked PRs when they should merge separately); the design names the docs the feature must update; the hand-off message says how the work will be delivered.
- `docs/delivery.md` (new): human guide: setup, verify.py and pr_prepare.py usage, both JSON contracts, the audit block, limits.
- Config schema `kitlib/schema/3-pr-delivery.json`; `.claude/loop.config.md` and `examples/loop.config.md` regenerated. `.gitignore`: `.claude/pr/` (PR bodies and saved verify results; not committed, because a committed body would carry a head sha that the commit itself makes stale).
- Tests (148, about 30 s of work in total, run in parallel by `tools/test.sh`; the whole suite is 1015 tests in about 25 s): `tests/verify/` (definition at the base sha, stages, environment scrub, process groups, ports, native dev server, gate toggle, log redaction, CLI, hardening, and the hello-loop fixture run end to end for F1-F3 using its own `verify.json`), `tests/pr_prepare/` (body rules, disguise corpus, paths, trailers, git checks, reports, H3, verify result, CI-fix, init, CLI, never-pushes), `tests/test_delivery_templates.py`.

## Upgrade impact

None for an installed v1.2.0 copy beyond new files and new keys with defaults that change no behaviour: `delivery: local`, `git_autonomy: none`. A v1 `loop.config.md` loads unchanged. To use the lane: fill `verify_tests` (and optionally the other `verify_*` keys), commit that config to the default branch (verify reads it there), set `git_autonomy` and `delivery`, add `.claude/pr/` to `.gitignore`, install the workflows (`docs/delivery.md`). The v1 key `git_strategy` stays as it was (the loop's strategy); `delivery` governs the interactive lane until `loopctl` unifies them (R5).

## New config keys

All owner phase `3-pr-delivery`, all H6-protected, none evidence-gated. Sections "Delivery" and (existing) "Verification".

- `delivery`: enum `local | push-branch | draft-pr`, default `local`.
- `git_autonomy`: enum `none | branch | branch+commit`, default `none`.
- `max_ci_fix_attempts`: int, default `2`.
- `always_human_paths`: list of globs, default `[]` (extra to the kit's built-in H3 list). **Registered here: Phase 4a must not register it again** (a duplicate name is a load error).
- `verify_build`, `verify_lint`, `verify_typecheck`: command, default `""` (empty = stage does not run). `verify_dev`: command, default `""`.
- `verify_require`: list, default `[tests]` (stages that must not be skipped). `verify_ports`: list of ints, default `[]`. `verify_ready_path`: string, default `/`. `verify_timeout_s`: int, default `600`. `verify_run_timeout_s`: int, default `120`. `verify_env_allow`: list of variable names, default `[]` (credential-shaped names refused at run time).

`verify_tests` and `verify_run` are the v1 keys and keep their meaning. `merge_policy`, `pr_granularity` and the `pr-automerge` delivery value are not registered here (L5 is design-only by IMP-1; the loop owns slice-level PRs).

## Decisions made

- **`delivery` values.** The brief said `local | branch | draft-pr`; the report (R5) says `local | push-branch | draft-pr | pr-automerge`. I used the report's names and left `pr-automerge` out (L5 enabling is design-only, IMP-1). `git_autonomy` has all three report values (`none | branch | branch+commit`).
- **`always_human_paths` is registered here**, because the PR audit block needs the H3 list and no other phase had registered it. The kit's built-in list (plus Phase 1's deploy-surface floor, imported when available) always applies; the key only adds. Phase 4a must reuse it.
- **Where verify gets per-item commands.** From config at the base sha for repo-wide stages and from an items file for per-item ones, in the shape hello-loop already ships. Plan items (`plan/items/<id>.json`, Phase 4a) will supply the same three fields (`tests`, `demo_route`, `ac_ids`). `ac_ids` are echoed, not evaluated.
- **`verify_require` defaults to `[tests]`.** An unconfigured optional stage is "skipped" in the result; a required one is an error. Smoke is optional by default because v1 projects without a harness would otherwise break; set it required once you have one.
- **Failure classes** map to loopctl's taxonomy: `config` and `env` mean the code is not at fault (no engineer retry); a port that stays bound or a process that outlives its stage is `leak`.
- **Exit codes:** 1 for any stage failure including `env`; 2 only when the definition is unusable.
- **Config drift and kit changes are flagged, not blocking.** The gate always uses the base copy, so a branch cannot weaken it; routing the change to a human is the job of CODEOWNERS and loopctl's G5.
- **`--allow-head-config`** exists for a project that has not committed its config yet; the result then says `trusted: false` and `pr_prepare` refuses to ship on it.
- **The PR body lives in `.claude/pr/<slug>.md`, gitignored**, not in the feature folder: a committed body would name a head sha its own commit makes stale. The saved verify result sits beside it.
- **Feature folders may be untracked.** Untracked files under `docs/features/<slug>/` do not make the tree dirty; modified tracked files do.
- **Interactive trailers** are `Feature`, `Engineer`, `Report` on WIP commits and `CI-Fix-Of` (also recorded in the audit block, because a squash drops trailers). `Loop-Item`, `Loop-Run` and `Loop-Attempt` stay the loop's.
- **Squash merges are assumed.** The body survives a squash only if the repo uses "PR title and description" (the Phase 1 boundary script sets it).
- **Local evidence is forgeable** (a body, a report and a verify JSON are files in the agent's tree). They catch mistakes and staleness. CI is the evidence (DEC-10); the audit block's `CI evidence` field says `PENDING` until the PR exists.
- **`claude-review.yml` runs the CLI directly**, not claude-code-action, because the action's inputs could not be verified offline and the kit already knows the CLI flags it wants; the CLI version is pinned by a repository variable tied to the canary (CO-10). Trigger is a maintainer's `/review` comment, per DEC-32 ("optional").
- **`verify.yml` takes `verify.py` from the base sha** (`git archive`), so a PR cannot replace the gate it runs under. The cost: the PR that installs the kit cannot pass.
- **Hostile-repo hardening** copies the doctor's: no fsmonitor, no hooks, no external diff or textconv in any git call. Tests plant such a config and prove nothing runs.
- **Doctor suggestion not built.** DEC-1 says the doctor suggests `draft-pr` once the ruleset checks pass; adding that check means editing `doctor.py`'s import line, a Phase 1 file that Phase 2 also needs. Listed under pointers.
- **Not built, by design:** per-AC parsing and "skipped count non-increasing / base test-name subset" (G1/G3/G5, Phase 4b); migrations up/down/up (Phase 4b's `loopctl gate migrations`); labels beyond refusing approver-only ones (the label list and apply script are Phase 11a's); output size limit on a stage's log file (a runaway test can fill the temp directory; the stage timeout bounds it).
